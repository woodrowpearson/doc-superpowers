# Release Notes

## v3.11.0 (2026-10-28)

This release lets a repository require doc-search: an agent stops while doc-search cannot answer, instead of working around it. Two new config keys set the policy, `doc-search check` decides one verdict, and the opt-in `--search-gate` hooks act on it in Claude Code and Codex. The gate applies only to a developer whose client finds doc-superpowers; for everyone else the committed hooks do nothing. A repository that does not set `"required": true` sees no change.

The decision is mechanical because rule text alone did not hold. Fresh agents under deadline pressure, given a hand-written "search first" rule, carried on past a stale index and an outdated launcher in 2 of 2 runs ("a stale cache isn't one of the listed outages").

### Upgrading from 3.10.0
Nothing changes until a repository sets `"required": true`. `doc-search init` still writes a config without the new keys, so a 3.10.0 teammate can read it.
- **`hooks install --search` users:** `scripts/search/launch.sh` changed, so the committed `.claude/doc-superpowers/search-mcp.sh` reads `outdated` in `hooks status --search`. Re-run `hooks install --search` and commit the launcher.
- **Requiring doc-search** needs every opted-in developer on 3.11.0 or later:
  - 3.10.0 and older reject the new keys: every tool and CLI verb answers `invalid config: unknown key required` (or `requires`). That message is the cue to update.
  - 3.10.0 and older have no `check` or `gate` (an unknown verb, exit 3). Run through an older launcher copy, or directly, nothing gates such a developer: the gate is silently absent for them.
  - The 3.11.0 launcher answers for an older plugin itself. Where the config is required, `check` exits 1, the session-start hook tells the agent to stop, the prompt hook blocks and the tool hook denies, with `doc-superpowers <version> predates the readiness gate` and the plugin update as the fix (`claude plugin update doc-superpowers`, or `git -C ~/.codex/doc-superpowers pull` for the Codex root).
- **The gate's hooks:** run `hooks install --search --search-gate` and commit `.claude/settings.json` and `.codex/hooks.json`. The session-start hook carries `--client claude` or `--client codex`; an entry without it reads `partial` in `hooks status --search-gate`, and re-running the install replaces it.
- **The agent rule:** copy the marked block of `references/search-rule.md` into `AGENTS.md` or `CLAUDE.md` and commit it. `hooks status --search-gate` says whether the copy is current.
- **`doc-release.yml`** may now also commit `scripts/search/launch.sh` and `references/search-rule.md`, the two files `bump-version` stamps in the doc-superpowers tree. A project has neither file, so nothing changes for it.

### Added
- **Two config keys** (`docs/search/config.json`; `references/search.md` → *Configuration*). `"required": true` makes doc-search a gate in this repository; the default `false` keeps the soft behavior. `"requires": ">=X.Y.Z"` is a version floor for the plugin and for the committed launcher copy; the default `null` sets none.
- **`doc-search check [--format text|json] [--budget 1-600]`**, the readiness probe (`references/search.md` → *CLI* → `check`).
  - Exits `0` ready or degraded, `1` not-ready (with one fix command), `3` usage, `4` not in force (no doc-superpowers for this developer, no config, or not required).
  - Ready means a valid config, the plugin and the launcher copy at or above `requires`, and both indexes matching the tree. Degraded: the static docs index serves while a transformer index builds, or the launcher copy differs from the plugin's but meets the floor.
  - Where required, a stale index gets one incremental refresh, bounded by `--budget` (default 20 s). `check` never starts a first build, and where doc-search is not required it refreshes nothing.
  - `--format json` gives the state, reason, fix, version, the launcher's state, each client's MCP state and the index states.
- **`doc-search gate session-start|prompt|tool`**, what the client hooks run.
  - `session-start` adds the verdict as context; not ready, it tells the agent to do no work until it is.
  - `prompt` blocks the prompt while not ready, with the reason and the fix.
  - `tool` runs no Python: it reads a per-worktree verdict file (`$(git rev-parse --git-path doc-search-gate)`) and, while it says not ready, denies every tool call but the launcher's `index`, `status` and `check`. `check` keeps that file too, so the halt's own fix followed by `check` lifts the gate.
  - The launcher answers `check` and `gate` itself where doc-search cannot run: no root, no `uv`, or an older plugin.
- **`hooks install --search-gate`** (`references/hooks.md` → *doc-search gate set*). It registers the three hooks (`SessionStart`, `UserPromptSubmit`, `PreToolUse`) in `.claude/settings.json` and `.codex/hooks.json`, merged per handler, both committed.
  - It is never part of `--all` or `--search`, and is refused without the config, or without the plugin's own launcher copy (unless `--search` runs with it and writes that copy first).
  - `uninstall --search` alone is refused while these hooks are installed: `uninstall --search-gate` first, or both together.
  - `hooks status --search-gate [--json]` reports each file (`installed`, `partial`, `absent`) and the rule copy (`.tiers.search_gate`).
- **The agent rule** `references/search-rule.md`: a block a project copies between `<!-- doc-superpowers:search-rule vX.Y.Z -->` and its closing marker. It is keyed to `check`'s exits and names the two cases `check` cannot see (the MCP tools missing while expected, and the wrong worktree). The status drift check compares the lines between the markers.
- **The Codex root.** The launcher also finds doc-superpowers at `${CODEX_HOME:-$HOME/.codex}/doc-superpowers`, after `$DOC_SUPERPOWERS_ROOT` and the repository itself and before the Claude Code plugin cache, so a Codex-only developer needs no variable (`.codex/INSTALL.md` → *doc-search*).
- **Two per-developer variables**, usually set in the launcher's env hook. `DOC_SEARCH_MCP=0`: this developer's client cannot run the MCP server, so `check` reports its MCP state as `off` and the rule does not halt on missing tools. `DOC_SEARCH_GATE=0`: the hooks allow everything for this developer and leave the verdict file alone.
- **Version stamps.** Line 2 of `scripts/search/launch.sh` is `# doc-search launcher vX.Y.Z`, and the rule's opening marker carries the version too. `doc-tools.sh bump-version` writes both and `check-version` checks both, only in the doc-superpowers tree (a project's own files of those names are left alone).

### Other
- What is verified for Codex: the `.codex/hooks.json` shape was checked offline with codex-cli 0.163.0 (its `hooks/list` loaded the three hooks in a trusted project and none in an untrusted one). The hooks have not been seen firing in a live Codex session, and which tools Codex sends through `PreToolUse` is not verified. Cursor is unverified.
- The rule's wording was tried with fresh agents, one fresh context per run, five runs per case: the MCP tools missing while expected, a launcher below the floor, doc-superpowers not installed, a first transformer build only the user can run, and Codex without the MCP entry. Each case got the intended answer in 5 of 5. Without the rule, the tools-missing case halted in 0 of 5.
- Known limits, left for later: a launcher copy newer than the plugin's is refused by `install --search-gate` with a message that calls it older; for a development checkout set as the root, the fix names `claude plugin update`; the rule's excuses table does not name the client in its `mcp:` row.
- Suite counts are in CLAUDE.md. The full local `check-ci.sh` passed under bash 5.x and `/bin/bash` 3.2: seven suites, 15524 assertions (from 14896), `test-hooks.sh` 4243, `test-doc-tools.sh` 1656, `test-spec-status-model.sh` 1045, the other four unchanged; doc-search's pytest suite, 863 passed with the 2 live tests skipped. GitHub Actions does not run on this account (billing lock), so this release was verified locally.

## v3.10.0 (2026-10-26)

This release adds `setup` and `help` (#51, phase 1 of #54). `setup` turns doc-superpowers on in a repository in one pass, with fixed safe defaults, and shows every write before it makes one. `help` is a one-screen map of every feature. Both work from the skill (`/doc-superpowers setup`, `/doc-superpowers help`) and from a terminal (`scripts/doc-superpowers`), with the same text.

The defaults are the same on every repository and host: the doc-index merge driver, the 5 git hooks and the 3 Claude hooks, all report-only. A default run downloads nothing, calls no network, adds no CI and blocks no commit; the hooks suite proves it with recording stubs for every download and network tool, a git wrapper that refuses every remote verb, and a transport trap that catches git run inside hooks. Everything else is opt-in: doc-search (static or the gte model, with consent before any download), the doc-search entries for Codex, Cursor, OpenCode and Gemini CLI, CI workflows, the work ledger, spec claims, and a `~/.local/bin/doc-superpowers` terminal command (asked first).

### Upgrading from 3.9.0
Nothing changes until someone runs `setup`: a marketplace install still writes nothing to any repository.
- **A repository already set up by hand:** `setup` starts from the defaults plus what is installed, so a plain run removes nothing. Its first write adds a `setup` object to `.claude/doc-superpowers/installed.json`; `schema_version` stays 2, and 3.8.x / 3.9.0 installers keep the object when they rewrite the file.
- **Teammates** run `scripts/doc-superpowers setup --apply` (or `/doc-superpowers setup`) to reproduce the recorded setup. It installs the per-user parts and changes no committed file.

### Added
- **`doc-superpowers setup`** (`references/setup.md`). The flow is Summary → Customize (a tree with a details pane) → Esc back to the summary with changes marked → Review, split into *Committed for the team* and *Local to you*, with the network and downloads named → *Write and build* / *Write only* / *Back*.
  - A TUI in portable bash 3.2; a numbered-prompt UI when there is no TTY, under `TERM=dumb`, or with `--plain`.
  - Flags: `--dry-run`, `--yes`, `--apply`, `--build` (the download consent outside the UIs), `--set id=value`, `--list`, `--for-team`, `--link-bin` / `--no-link-bin`. Exit codes 0 done or nothing to do, 1 refused (nothing written), 2 a step failed (re-run finishes), 3 usage.
  - The team's choices go in `installed.json` (`setup`), each user's in the untracked `installed.local.json`. Per-user items (git hooks, Claude hooks, the ledger hook sets) change only your record unless you choose *for the team* (`--for-team`); adding or removing the merge driver is always the team's.
  - Host checks only disable an option and say why (no `uv`: no build; gte below macOS 14 on Apple silicon; a global or work-tree `core.hooksPath`: the merge driver alone). Scan hints never change a default.
  - setup never deletes what it did not write: unticking a harness removes only its `doc-search` key or setup's marked Codex block, and leaves your own entries alone.
- **`doc-superpowers help [topic]`**: an overview within 24 lines, and the topics setup, search, hooks, ci, ledger, claims, release. `/doc-superpowers help` prints the same file verbatim.
- **`scripts/doc-superpowers`**: the dispatcher every client runs (`help`, `setup`, `version`, and the `hooks`, `tools`, `search` pass-throughs). A plugin cannot put a command on the terminal's `PATH` (a plugin `bin/` reaches only Claude's Bash tool, and would stop claude.ai and Cowork from installing the plugin), so `setup` offers the `~/.local/bin` shim, which finds the newest plugin version at run time.
- **The skill's `setup` and `help` actions**, and two evals (`setup-defaults`, `help-topic`).

### Fixes
- **`references/search.md` → *Other clients*** now says what was checked against each client. Codex (codex-cli 0.163.0) loads a project's `.codex/config.toml` only for a trusted project, and starts servers in its launch directory, not the project root. Gemini CLI 0.65.0 and OpenCode 1.19.4 load and connect from the repository top. The OpenCode entry now `cd`s to the top first, so it also connects from a subdirectory. Cursor stays unverified.

### Other
- Suite counts are in CLAUDE.md; the full local `check-ci.sh` passed under bash 5.x and `/bin/bash` 3.2 (Actions cannot run on this account: billing lock). The util-linux path of the TUI's terminal-restore test has not run yet: it runs on the ubuntu CI leg.
- The workflow and architecture diagrams still show the action set before `setup` and `help`; their prose says so.

## v3.9.0 (2026-10-24)

This release makes two changes. `hooks install --ci` stops writing a personal GitHub URL into a project (#56), and doc-search searches the MCP client's worktree when a call names none (#58).

A client project installed only `doc-ledger-publish` and still received `.github/scripts/doc-superpowers-steps/prepare-agent.sh`. That workflow never runs the script, and its default marketplace URL names the maintainer's GitHub account. The project forbids personal identifiers in its repository, so the file had to be dropped by hand, and the next `install --ci` would have vendored it again. Now `install --ci` vendors only the step scripts the installed workflows run. No shipped file names a URL any more: the AI workflows get their marketplace URL from the installer.

doc-search's default worktree used to be the one the server started in. The Claude desktop app starts a project's MCP servers in its main checkout (`claude --project-config-root <main checkout>`) while the session works in a worktree. So every `search`, `fetch` and `related` without `worktree` read the main checkout's files, and the cloud leg's branch-changed filter ran against the wrong tree too. Nothing flagged it: when both trees were at the base branch the answers matched, and otherwise the session got another tree's text.

### Upgrading from 3.8.1
Re-run the installs you use and commit what they write. Nothing breaks until then: the 3.8.1 workflows, step scripts and launcher keep working as they are.
- **`hooks install --ci`:** one run refreshes every managed workflow and vendors their step scripts together.
  - **AI workflows** (`doc-audit-update`, `doc-review-pr`, `doc-release`, `doc-spec-verify`, `doc-pr-full-cycle`, `doc-pr-release`) gain an env line, `DOC_SUPERPOWERS_MARKETPLACE_URL: "<url>"`. By default it is the plugin's own repository (`.claude-plugin/plugin.json` → `repository`, with `.git`), the same URL the old `prepare-agent.sh` defaulted to, so the plugin is fetched from where it always was.
  - **`prepare-agent.sh` has no default URL any more.** With `DOC_SUPERPOWERS_MARKETPLACE_URL` unset it fails with `::error::doc-superpowers: DOC_SUPERPOWERS_MARKETPLACE_URL is not set …`. That only happens if the new copy is vendored without re-rendering its workflow (copied in by hand, say); `install --ci` always writes both.
  - **Unused step scripts go.** A 3.8.1 install vendored all eleven step scripts. The re-run removes each one no installed workflow runs, when it is byte-identical to the plugin's copy. A copy that differs is kept and reported (`Kept …`). That includes every 3.8.1 `prepare-agent.sh`, since its default-URL line changed. `hooks status --ci` then lists it as `⚠ .github/scripts/doc-superpowers-steps/prepare-agent.sh: no installed workflow runs it — removable`: delete it and commit.
  - **The two default shell workflows** change only their comment footers. The freshness PR comment and the scheduled audit issue now end `*Generated by doc-superpowers*` (and `… scheduled audit*`), without the repository link. Existing comments and issues are still found by their marker.
- **`hooks install --search`:** `scripts/search/launch.sh` changed, so the committed `.claude/doc-superpowers/search-mcp.sh` reads `outdated` until the re-run. A server started by the old launcher keeps the old default. A project rule that tells agents to pass `worktree:` on every call can drop that once the new launcher is committed; passing it stays harmless.

### Fixes
- **Step scripts follow the workflows one by one** (#56).
  - `install --ci` vendors each step script in `.github/scripts/doc-superpowers-steps/` that an installed workflow names outside a comment. A `hashFiles(…)`-guarded reference counts only when another workflow ships the script.
  - It also vendors, transitively, each sibling one of those scripts runs as `"$(dirname "$0")/<name>.sh"` (`prepare-agent.sh` snapshots `commit-changes.sh`).
  - The list is read from the workflow and script files, not kept by hand. `doc-ledger-publish` alone ships `ledger-publish.sh` and no other.
  - `uninstall --ci --workflows=<name>` removes the scripts only that workflow ran (byte-identical only).
- **No shipped file names a personal URL** (#56). The marketplace URL moved from `prepare-agent.sh`'s default into the AI templates' env, rendered at install time. The freshness footers lost their link. A test now fails if any template, step script, helper or vendored tool names the plugin owner's account, or if anything `install --ci` writes names it outside that rendered env line.
- **doc-search's default is the client's worktree** (#58; `references/search.md` → *Tools* → `worktree`).
  - **The launcher.** For `serve`, it exports its parent process's working directory as `DOC_SEARCH_CLIENT_CWD`, unless that is already set. It reads `/proc/$PPID/cwd` on Linux and falls back to `lsof -b`.
  - **Who the parent is.** It is the MCP client both for the entry `install --search` writes (`sh <launcher> serve`) and for an `sh -c` wrapper that `exec`s the launcher. A wrapper without `exec` is the parent itself, and so is an IDE extension host whose cwd is elsewhere. The default then stays the launch worktree: set `DOC_SEARCH_CLIENT_CWD` in that entry.
  - **The server.** When the client's directory is in one of this repository's worktrees, that worktree becomes the default for every tool and its indexes warm first. A directory anywhere else, or none, keeps the launch worktree.
  - **Arguments.** A `worktree` argument still wins, and a relative one is read against the default, so `.` is the client's worktree, not the launch one.
  - **The config** is still the launch worktree's, so a branch cut before a project adopted doc-search is searchable too.
  - **A default worktree removed** after the server started is refused on the next call, never swapped for the launch one.
- **`status` names the default** (#58). The default worktree is listed first, with a `default worktree: <path> (the client's working directory; the server was launched in <top>)` line. When the client's directory could not be used, the reason reads `(the client's working directory <dir> is not a worktree of this repository)`. For a removed default it reads `(the default worktree <path> is no longer a worktree of this repository; pass worktree)`, and the launch worktree is reported in its place.

### Added
- **`hooks install --ci --marketplace-url <git URL>`** (#56): where the AI workflows fetch the plugin, at its release tag. For a project that keeps personal identifiers out of its files, point it at a mirror you control that carries the release tags.
  - It is recorded in `installed.json` as `.tiers.ci.marketplace_url`, only when given (the default is never recorded), and a plain `install --ci` keeps it. `--marketplace-url=` clears it.
  - The value may contain letters, digits and `. _ ~ : / @ % + = , -`, and must not start with `-`. Anything else exits 1 and writes nothing.
  - `status --ci` shows it among the choices; `status --json` shows it as `.tiers.ci.choices.marketplace_url`.
- **`hooks status --ci` reports unused step scripts** (#56). A vendored step script that no installed workflow runs reads `⚠ <path>: no installed workflow runs it — removable`. `status --json` lists it in `.tiers.ci.removable_vendored`, a new key in the `doc-superpowers-hooks-status/1` shape.
- **`doc-tools.sh tools install|uninstall --step <script>`** (#56; repeatable, `.sh` optional). It installs or removes only the named step scripts of `doc-superpowers-steps`, exactly as named, instead of `--helper doc-superpowers-steps`. Combining `--step` with `--helper`, or with `--with-helpers`, exits 2. `tools uninstall --step` reports each named script it keeps. `install --ci` uses it, one `--step` per script its workflows run.
- **`DOC_SEARCH_CLIENT_CWD`** (#58): the MCP client's working directory, whose worktree becomes doc-search's default. The launcher sets it for `serve`. Set it yourself for a client the launcher cannot see (*Configuration* → *Environment*).

## v3.8.1 (2026-10-22)

This release keeps the doc-search servers on one host from rebuilding the same index at once (#50). Every client session runs its own `doc-search serve`, and the servers over a worktree share semble's cache. After a ~320-commit fast-forward of abundance-mvp's main checkout on an Intel Mac, all 7 servers over it rebuilt the same docs and code indexes together: combined RSS went 10.6 → 12.9 GB in 40 s, swap reached 28.2 GB and the root disk fell to 228 MB free. Now one server builds each index and the others load what it saved.

### Upgrading from 3.8.0
Nothing breaks, and no config, hook, CI template or vendored script changed. `scripts/search/launch.sh` is unchanged, so an installed `--search` launcher stays `current`; servers pick 3.8.1 up at their next start.
- **What a waiting server answers.** A first build waiting for another server's build of the same index answers `doc-search: index building … retry shortly`, the same line as any first build, until the holder has saved; then it loads the saved index. A rebuild waiting for it is not waited for: the previous index serves. A readiness probe (abundance-mvp's `docs/runbooks/mcp-readiness-gate.md`) therefore sees "building" for the length of one build, not N concurrent ones.
- **A new file beside each index:** `<index dir>.lock` in semble's cache, a few bytes holding the holder's pid. Do not delete it while servers run.
- **A new warning** in a server's log when a holder is alive but stuck for an hour: `doc-search: the build lock <path>.lock is still held by pid <n> after 3600 s: building without it`.

### Fixes
- **One static build per index per host** (#50; `references/search.md` → *Hardware and performance* → *One build per index per host*):
  - **The lock.** A build holds an exclusive `flock` on `<index dir>.lock` from its slot until it has saved and stamped the index. It covers every static build: the docs index, the code index, and the static docs fallback a transformer build serves meanwhile. A transformer docs build keeps 3.8.0's host encoder lock.
  - **One lock per physical directory.** The lock path is resolved through symlinks each time the lock is taken, so a cache reached through a link (`~/Library/Caches/semble` → another volume) or named by `SEMBLE_CACHE_LOCATION` keys one lock.
  - **No duplicate build after a wait.** Inside the lock the cache is checked again: when another process saved it meanwhile, the index is loaded, not rebuilt. Build seconds, and so the recheck cooldown, count from the lock.
  - **Holders that crash or hang.** A holder that dies releases the lock with its process. One that is alive but stuck is waited for at most an hour, then the waiter builds without the lock. Where `fcntl` is missing (Windows), or the lock cannot be set up (an unwritable cache, a filesystem without `flock`), the build runs without it after one warning.
  - **Lock order:** a slot, then the cross-process lock, then the entry's `save_lock` (the static fallback's save now runs inside its build lock).
- **A built index is stamped inside its lock.** Before, the stamp was read after the save, so a save by another process in between could lend an older in-memory index the newer stamp, and the next recheck kept it as current.

### Other
- Seven suites, 12860 assertions, under bash 5.x and `/bin/bash` 3.2, unchanged. doc-search's pytest suite goes from 761 to 768 tests (`search/tests/test_buildlock.py`).
- Not built:
  - **Locking the transformer validate-and-save** with the per-index lock. It would close 3.8.0's known window where a static fallback save in one process overwrites a transformer index another process just saved; this self-heals from the encode cache.
  - **Sharing an index between processes.** Each server still holds its own copy, 0.4–2.1 GB each measured on that host. Only `vectors.npy` could be memory-mapped; the BM25 archive and the chunk objects cannot be shared.

## v3.8.0 (2026-10-21)

This release gives doc-search an opt-in local transformer for its docs leg (#45): `docs.model: "transformer:gte-modernbert-base"`. It runs `Alibaba-NLP/gte-modernbert-base` (int8 ONNX, onnxruntime CPU) on the host, with a per-host encode cache keyed by each chunk's text, so a new worktree reuses every vector the host already encoded. On abundance-mvp's docs (194,564 chunks, 65 known-answer queries, k = 10) the local docs leg scores recall@10 0.846 / MRR 0.635, against 0.687 / 0.531 with semble's static model; fused with the cloud leg, 0.880 / 0.743. The launcher also sources a per-user env hook at every launch (#48), so a per-host cache location (`SEMBLE_CACHE_LOCATION`, `DOC_SEARCH_CACHE_LOCATION`, `HF_HOME`) reaches a server an MCP client starts without the shell profile. Static semble stays the default: a project that sets neither sees no change.

### Upgrading from 3.7.0
Nothing breaks, and the cloud leg is untouched: same chunker version, same embedder, so no cloud corpus needs re-embedding. No git hook, Claude hook, CI template or vendored CI script changed.
- **Projects with `--search` installed:** `scripts/search/launch.sh` changed, so the committed `.claude/doc-superpowers/search-mcp.sh` reads `outdated` in `hooks status --search`. Re-run `hooks install --search` to get the env hook and the `local-transformer` extra.
- **Turning the transformer on** is a config change, `"docs": {"model": "transformer:gte-modernbert-base"}`. Expect:
  - **A first build of hours per host.** On an M1 Pro, 3–5 h for abundance's docs (16 chunks/s quiet, 10 under heavy load). On an Intel Mac about 3.6 chunks/s, roughly 15 h. A static docs index serves meanwhile, and `status` shows progress and an ETA. Run `doc-search index` once with the static model before switching, so the first transformer build has a total to estimate from.
  - **A warm second worktree takes about two minutes on a loaded M1 Pro**: 99–117 s, every vector read from the encode cache (a quiet-host re-measure is pending).
  - **About 3.4 GB peak memory during a first build.** The ONNX session is dropped after each build that encoded something.

### Features
- **Local transformer docs model** (#45; `references/search.md` → *Modes* → *Local transformer*):
  - **Config.** `docs.model: "transformer:<name>"` against a built-in registry, with one entry, `gte-modernbert-base`, at a pinned revision. `code.model` refuses the prefix. `docs.threads` takes 1–256, or `null` for the performance cores less two (at least 2).
  - **The `local-transformer` extra** (onnxruntime, flatbuffers, protobuf). The launcher adds it when `docs.model` starts `transformer:`.
  - **Encoder.** It plugs in at semble's model loader. The saved index records the model with its revision (`transformer:gte-modernbert-base@e7f32e3c00f9`), so a registry change invalidates every saved transformer index.
  - **Encode cache.** A sqlite rowid table keyed by the sha256 of model id, variant, token limit, onnxruntime version, CPU architecture and text; query strings are never stored. A cache location that cannot be written degrades to no cache, with one warning, and never fails a build.
  - **One encoder per host.** A per-model `flock` lets one process encode at a time; another process serves its static index while it waits. A refresh waits at most 10 s for the lock, then encodes without it.
  - **Builds run in a lane of their own,** so code and other worktrees' static builds never wait behind an encode. A stale saved transformer index serves while it refreshes. The recheck cooldown is capped (60 s base); failures in a row back off 60, 120, 240 … s, up to 1 h. Evicting a worktree cancels its queued transformer build.
  - **Progress.** `status` shows chunks encoded, the encoder's rate, an ETA from the build's overall pace (cache hits included) and, before a build starts, a per-architecture estimate. A build in another process is read from a progress file. `index`, `query` and `eval` build in the foreground and print a progress line on stderr every 30 s.
- **The launcher's env hook** (#48). `launch.sh` sources `$DOC_SEARCH_ENV_FILE`, else `${XDG_CONFIG_HOME:-~/.config}/doc-search/env.sh`, before it resolves anything, so the hook may also set `DOC_SUPERPOWERS_ROOT` and `PATH`. It is read at every launch, so it can decide then: export a cache location only while its volume is mounted, say. A missing file is skipped. One that does not parse is skipped with one stderr line, and doc-search still starts. Its output goes to stderr.

## v3.7.0 (2026-10-21)

This release covers the two work-ledger use cases in #36 and #39: filing an item, and keeping items' relations up to date at merge time. `ledger new --create` writes the item file itself, and `/doc-superpowers ledger file` wraps it in a filing flow: duplicates first, then one question round, then the confirmed relations. `ledger upkeep` reads a range or a PR and proposes the `changes` / `consumes` relations its items are missing, each with evidence and a ready `ledger link` line. It never writes them. `/doc-superpowers ledger declare` confirms those proposals with a person and links them. On pre-push, `validate --pushed` gains an advisory for contracts a push touches that no involved item declares. It never blocks. On 23 real abundance-mvp PRs, two blind judges rated 0.78 / 0.74 of upkeep's proposals correct at `--top 0` (0.74 / 0.68 at the default `--top 3`), against a bar of 0.6. The design spec's *Acceptance* section has the details. A project without `docs/ledger/config.json` sees no change.

### Upgrading from 3.6.0
Nothing breaks. On a ledger host:
- **Pre-push gets slower.** The ledger pre-push leg now runs the `undeclared-contract-change` advisory. It is skipped for an empty range and for a tip the base already holds. On abundance-mvp, the first push of a branch takes about 25 s cold and 6–7 s warm; a per-PR `upkeep` takes about 22 s cold and 4 s warm. To opt out, set `validate.undeclared_contract_change: false`. Any other non-default value gives one `could not check` advisory.
- **Touched means named.** A contract counts as touched only when an added or removed line of its `defined_in` file names it. A contract the code never spells out (a component, a pattern) needs a `Contract-Change: <id> — <line>` trailer.
- **Spec and ADR amendments raise advisories (D9).** Some contracts are defined by one document: a literal path, or a glob that matches exactly one file, that no other contract shares. Any edit of that document touches the contract. The amendment's owner comes from:
  - the plans its changed lines cite, by repo path or relative link;
  - the claims trailers on the commits that edit it.

  When neither reaches an item, the contract is listed in `unattributed_contracts` with `cites`; it is never guessed.
- **Plan convention.** A plan links an item through a frontmatter value (or list element) that is the item's key, alias or path, or through a Related work row marked exactly `include`. Key words in the plan body don't count. New plans should carry frontmatter `issue: <key>`. If your plans record their item only in host-specific fields, add an `issue:` line. For example, abundance-mvp's `ledger:` + `ledger-row:` plans get theirs from `docs/ledger/legacy.json`: `{"key": K}` → `issue: K`, `{"item": P}` → `issue: P`, archived → skip, no entry → list it for a human.
- **Plans are found through the doc-index** (`doc_columns.plan` types and globs). A `docs/.doc-index.json` that is present but invalid makes `upkeep` exit 2 whenever the net diff holds a `.md` file, and the advisory reports `could not check`.
- **In-flight caches** are recomputed once after the upgrade, because their signature changed.
- **Known limitation (B1).** When `<b>` is not HEAD (`--pr` from another checkout, or `ledger declare --pr`), contracts from `adapters.contracts` come from the checked-out tree. Run from the PR's head.

## v3.6.0 (2026-10-20)

This release adds **doc-search**, an opt-in MCP server that answers "where is this specified, and where is it implemented" with one ranked list of docs and code. It keeps two semble indexes per worktree (docs and code), adds an exact-identifier docs leg and, optionally, a Vertex + Firestore cloud docs leg, fuses them by file, and puts the doc-index's cross-links on each hit. On abundance-mvp's corpus (6,513 docs, 66 known-answer queries) the fused docs search scored recall@10 0.927 / MRR 0.764, against 0.889 / 0.740 for the cloud-only search it replaces and 0.783 / 0.558 for one shared index (design spec §12). A project that does not turn it on sees no change, and the doc-superpowers core still needs no Python.

### Upgrading from 3.5.0
Nothing breaks and nothing needs re-running: no hook script, CI template or vendored script changed. `install.sh status --json` gains `.tiers.search`, only when `--search` is named (the schema stays `doc-superpowers-hooks-status/1`). To turn doc-search on, see `references/search.md` → *Turning it on* (it needs `uv`).

### Features
- **doc-search** (`search/`, a uv package on the MCP Python SDK v2: `semble`, `mcp`, `pathspec`; no torch, no onnxruntime). `docs/search/config.json` turns it on per repository; `{}` is a complete config, and an unknown key is an error that names it. Without the config every tool and CLI verb is inert. `references/search.md` is the reference.
  - **Tools:** `search` (docs, code or both; `doc_type`, `path_prefix`, `include_terminal`, `worktree`), `fetch` (a line range of a file in the worktree; git-ignored files are never served), `related` (the code a doc describes, the docs that cover a code file, similar passages) and `status`.
  - **CLI:** `doc-search init | index | query | status | eval | serve`, through the committed launcher. `status --format json` is a readiness probe (`ready`, each cache `valid` / `stale` / `absent`) that never builds or waits. `eval` scores recall@k and MRR over a JSONL of known-answer queries, with a one-shared-index leg for comparison.
  - **Local legs:** two semble 0.7 indexes per worktree, built from the working tree and refreshed incrementally; an exact-identifier docs leg (spec IDs, issue keys, file names; front matter, then path, then title); reciprocal-rank fusion by file with a per-kind floor, so neither kind crowds the other out. At most two worktrees' indexes stay in memory and one build runs at a time; a search during a build answers from what is ready and says so.
  - **Cloud leg** (the `cloud` extra: `google-genai`, `google-cloud-firestore`): Vertex `gemini-embedding-001` query embeddings and Firestore `find_nearest` over a `doc_chunks` collection compatible with abundance-mvp's. It runs beside the local legs under `cloud.timeout_s` (default 20); hits on files this branch changed are dropped so the local legs serve them fresh; a failure is remembered for 60 s. It turns gRPC's fork support off (`GRPC_ENABLE_FORK_SUPPORT=false`, unless already set), since with it on a git child forked while the client was live sometimes died before exec. `DOC_SEARCH_CLOUD=0` turns it off on one machine.
  - **Cloud write path** (`index --cloud`, the CLI only): it indexes HEAD's blobs, from the base branch only. The corpus stamp decides between a catch-up and a full run, so a stale clone never rolls the shared corpus back. The stamp records `repo_id` and `chunker_version`; a transactional 30-minute lease keeps two hosts from writing at once; orphan pruning stops at max(20, 10% of the corpus).
- **`hooks install | uninstall | status --search`**: the opt-in doc-search set (never in `--all`; refused without `docs/search/config.json`). It writes a committed POSIX launcher, `.claude/doc-superpowers/search-mcp.sh`, which finds doc-superpowers at run time (`$DOC_SUPERPOWERS_ROOT`, this repository, or the newest plugin-cache version), and a `doc-search` entry in `.mcp.json`. `references/search.md` has snippets for Cursor, Codex, OpenCode and Gemini CLI (unverified).
- **Skill wiring:** SKILL.md reads `references/search.md` when `docs/search/config.json` exists. `audit` and `review-pr` use a connected server's `search` and `related` as leads to read, never as evidence.
- **Hardware:** an Apple-silicon Mac is the minimum supported host; Intel Macs and Linux work, slower. On an Intel mini, both indexes of a ~6.5k-doc, ~5.7k-code-file repository build in about 3 minutes; a query takes milliseconds.

- **`check-ci.sh search`** runs doc-search's pytest suite (`uv run --frozen`). `DOC_SP_REQUIRE_UV` (default 1) makes a missing `uv` a FAIL; `0` turns it into a loud SKIP. `tests.yml` runs the check after `astral-sh/setup-uv`, pinned by sha.

This release follows up the work ledger that 3.3.0 introduced. A project without `docs/ledger/config.json` sees no change. A ledger host that sets none of the new keys sees the changes listed under *Changed (ledger hosts, without opting in)*. One of them can turn a passing step red: `notices --gate` now exits 2 when its in-flight fetch fails. The version is 3.4.0 rather than 3.3.1 because it adds flags and config keys (semver minor).

### Upgrading from 3.3.0
Nothing breaks if you skip these steps. What each host re-runs, and why:
- **A per-user `--ledger-claude` install**: re-run `hooks install --ledger-claude`. The state-watch hook is now registered for `Write|Edit|MultiEdit`. Until the re-run, MultiEdit writes are not watched, and `hooks status` (and `status --claude`) reads `outdated (registered for other tools than matcher "Write|Edit|MultiEdit")`. The re-run replaces the entry in place.

Pin `>= 3.4.0`. A contributor still on 3.3.0 skips the `require_relations` check without a word. A script's new forms fail on 3.3.0: an unknown flag (`--top`, `--relations`, `--suggest-contracts`) exits 3, and a comma list is one bad value (exit 1).

### Features (opt-in)
- **`ledger suggest <item> [--top N]`** (read-only) and **`ledger new … --suggest-contracts [--top N]`** propose the contracts an item might declare:
  - `changes` candidates are the contracts whose `defined_in` matches a file the item lists.
  - `consumes` candidates are the contracts that its related items (confirmed neighbours and the open candidates `related` lists) change or consume.
  - Each candidate comes with its reasons, and contracts the item already declares are left out.
  - Candidates rank by evidence (the number of reasons), then by contract id. `--top N` keeps the first N: the default is 15, and `0` shows all.
  - JSON: `{item, declared, total, truncated, candidates: [{field, contract, reasons, sources}]}`. The text output ends with a `confirm with: ledger link …` line and says `(showing N of M candidates; --top 0 shows all)` when some were left out.
  - Nothing is written: the caller confirms and writes with `link`.
- **Multi-value `link`**: `--consumes`, `--changes` and `--relates` each take a comma list, and any of the three can be given at once. A value that is itself valid is never split, so a contract id that contains a comma still works. Every value is checked first: one bad value means exit 1 and nothing is written. Otherwise the run makes one write and reads the index once.
- **`link <item> --relations none`** writes `relations: none`, the opt-out that `validate.require_relations` reads. It is refused next to another relation flag, or when the item already names a relation. A later `link` that writes a relation removes the marker in the same write (JSON `removed`).
- **`validate.require_relations: "new"`** (default `null`, off):
  - `validate --staged` (the pre-commit leg) blocks an added open item that names no `changes`, `consumes` or `relates` and has no `relations: none` (`no-relations`).
  - `validate --all` reports open items new since adoption as advisories. With no resolvable base, or an adoption commit beyond a shallow boundary, every open item counts.
  - Any other value is a config error (exit 2).
- **`init.stub_defaults`**: frontmatter fields that `init --accept` writes into each stub it creates. Each value is a string, number or boolean, and `{today}` in a string becomes the run's local date. The stub's own `status`, `key`, `ledger` and `summary` win.
  - A string that a YAML loader would read as another type (`true`, `no`, `off`, `null`, `~`, `007`, `1e3`, …) is written double-quoted, so it stays a string. Dates are written bare.
  - Bad values exit 2 before anything is written, `--dry-run` included.
  - abundance can drop the stub fields it filled in by hand.
  - With `require_relations` already on, add `"relations": "none"` here for an `init --accept` re-run, or the new stubs are blocked at commit.

## v3.2.0 (2026-10-14)

This release adds executable spec claims. A claim is one atomic, falsifiable statement quoted from a governing doc (a spec or an ADR), stored beside it, bound to a check, and judged at recorded gates in the spec lifecycle. When a doc and the code disagree, the direction is ruled and recorded on the claim before either side is edited. The feature is opt-in: a project turns it on by creating `docs/spec-claims/`. Without that directory every `claims` verb prints `{"verb":"<verb>","enabled":false,"exit":0}` and exits 0, and the hooks, CI templates and `spec-*` actions reach the same outcomes as in 3.1.0. What does change for every project is listed under *Changed (all projects)*: wording, a framing, a longer scheduled-audit timeout, claims steps that report `disabled`, two inert template comments, and `update-pr-body.sh` refusing content that holds a section marker. One fix reaches every project too: `deprecate-entry` keeps an existing `superseded_by` (*Fixes*).

### Features
- **`doc-tools.sh claims <verb>`, the claims checker** (`scripts/doc-tools.sh`, `references/spec-claims.md`). A claim lives in a sidecar, `docs/spec-claims/<DOC-ID>.json`. Its `quote` must anchor uniquely in the doc's live normative text. Its check is one of four tiers, ranked `test > lint > log > judge`. Its status (`built`, `diverged`, `unbuilt`, `retired`) fixes the result the check is expected to give: a `built` claim must pass, a `diverged` one must fail by an assertion, and an `unbuilt` one must not pass. The verbs:
  - `validate --staged | --all` runs checks V1–V12: schema, anchor, test binding, lint, status and tracker, a ratchet against the merge-base (a changed `states`, a lowered tier or a token-changing re-anchor needs a `DOC-STALE` or `RETIRE` ruling, a status off `built` a ruling of any direction; a claim is retired, never deleted), restatements, normative-line coverage, conformance wording in descriptive text, edits to a claim-bound test, configuration, the doc's status block, and plan structure. A finding blocks when its check is in config `blocking`: V1–V6 and V10–V12 by default.
  - `run` runs the checks (`--all`, ids, or `--planes-of <range>` for the claims a range touches) and judges each raw outcome by its claim's status. `--scheduled` adds the `log` claims and `--judge-sample <n>` names n `judge` claims for a reviewer, rotated weekly.
  - `promote <id>` is a test claim's only path into `built`. It refuses a dirty tree. In a throwaway worktree at HEAD, the bound test must pass unmodified and then fail by an assertion under a non-vacuity proof: a `mutant` edit of the subject, or `observed_red: <commit>`. The verdict goes to a local store, keyed by its sha256, and the sidecar gets the digest and `promotion.proved`, the fingerprint of the claim record it proved (see *The promotion fingerprint* below). `promote --reverify` re-runs the proofs and stores fresh verdicts, without writing the sidecar or the doc. A `lint`, `log` or `judge` claim is not promoted: it enters `built` (or `gated`) by a reviewed status edit, and its own check verifies it, as for any `built` claim. The chunk gate and `attest` run every such claim in the plan's scope that their range moved into `built` or `gated` — a claim its `**Claims:**` lines name, or any claim of a doc its Specs list (or `governing_specs:`) names, so no `**Claims:**` line need name it — and the gate records the status edit as reconciled.
  - `render [--check]` writes a generated `## Claim status` block into each doc with a sidecar. It lists every claim that is neither `built` nor `retired`, or reads `Claims: N built`.
  - `gate --plan <p> --chunk <n>` writes `docs/spec-claims/gates/<plan-stem>/chunk-<n>.json`, even when red. It runs the claims the chunk names, checks V8, V8n and V9 over the chunk's commits, and applies the record-inclusion rule: a ruling, promotion or status change the record does not include is a silent reconciliation, and a finding. `--holds <id> --by <principal>` records that an edited claim-bound test still holds.
  - `attest --plan <p> [--final] [--deep]` checks the records against the branch at HEAD. It matches their commits by `git patch-id --stable`, so a rebase keeps them, re-runs every claim the plan names, and checks that every ruling and promotion since the merge-base appears in a record. `--final` writes `final.json`, again even when red, so a ruling made at the final gate can cite it.
  - `rulings --range <a>..<b> [--format markdown]` prints the amendment batch, the `DOC-STALE` and `RETIRE` rulings the range adds, for the human who reviews docs.

  The `claims` verbs have their own exit codes: `0` as expected, `1` findings, `2` could not run (never reported as a pass, and never `1`), `3` usage, with precedence `1 > 2 > 0`. Each prints exactly one verdict JSON object. Every other subcommand keeps its exit table.
- **The promotion fingerprint, `promotion.proved`** (`scripts/doc-tools.sh`, `references/spec-claims.md`). `claims promote` records what it proved: the sha256 of each of the claim's `states`, `test`, `subject`, `nonvacuity` and `when` (their compact `jq -cS` JSON, `null` when absent), and its `enforced_by`. V6, `gate` and `attest` decide a promoted claim by comparing it with `proved`, field by field, and never read history (`promotion.at` is a record only), so a fresh clone, CI and a trunk the branch was squash- or rebase-merged onto all give the same answer.
  - A swapped `test`, `subject` or `enforced_by` is a finding that names the field, whatever the ruling. So is a changed `nonvacuity` or `when`, unless it comes with a covered `states` amendment.
  - A changed `states` under a new `DOC-STALE` or `RETIRE` ruling is the advisory `re-promote owed`, and `gate` and `attest` stay red until `promote` has re-proved the claim. Without that ruling it is a finding.
  - Where the local store holds the verdict, the verdict must also bind the claim, so a forged `proved` beside a real verdict is a finding. V6's advisory `unverifiable-here` is left for one case: the verdict is not in the store and nothing has changed since the proof.
  - V1 requires `proved`, with exactly its six keys, on a `built` or `gated` claim's promotion. It also requires every number in a `when` to be written canonically (`1.5`, not `1.50`, `1.0` or `1e3`; at most 15 significant digits): jq 1.6 and jq 1.7+ print other number literals differently, so the `when` digest would differ between them.
- **Adapters, fail-closed** (`references/spec-claims.md`). A host plugs its test frameworks in through small executables named in `docs/spec-claims/config.json`: a runner adapter (`list`, a static scan of the claim-bound tests; `run`; `edited-bound-tests`), and an optional log adapter. doc-tools calls each with stdin from `/dev/null` and every argument intact. Output it cannot parse, a missing outcome, or a non-zero exit makes every requested node `indeterminate` (exit 2). It is never a pass and never a finding. The reference ships example pytest and jest helpers that mark `diverged` claims as expected to fail on an assertion only, and `unbuilt` ones as expected to fail on anything.
- **The configuration extension**, off unless config names a `config_adapter`. It is for hosts whose production behaviour depends on recorded configuration (feature flags, deploy-manifest variables, build variants). A claim gains `when: {KEY: VALUE}` and the status `gated`: it holds under `when`, which production does not set yet. V3 adds configuration-faithful checks, V10 re-classifies the affected claims when a configuration surface changes, and `claims validate --config KEY=VALUE` previews a change published outside git.
- **The direction protocol** (`references/spec-lifecycle-protocol.md`). The directions are `CODE-DIVERGES` (the doc is the intent: fix the code, or defer the claim as `diverged` with an open tracker), `DOC-STALE` (amend the doc in a dated `AMENDED` block, with a reason) and `RETIRE`. A ruling is recorded on the claim with `date`, `direction`, `by`, `record` and `reason`. Host policy in `config.json` decides which record may license a `DOC-STALE` or `RETIRE`, and who may rule one outside a plan.
- **Hooks and CI** (`scripts/hooks/`, `references/hooks.md`). Every leg below runs only with `docs/spec-claims/`.
  - The pre-commit hook gains a claims leg (see *Changed (claims-enabled projects only)*).
  - The pre-push hook gains an advisory claims leg. It runs `claims run --planes-of` over the commits each pushed branch adds, and `claims attest --plan` for each plan with gate records but no `final.json`. It prints `claims (advisory): <n> red, <m> indeterminate` and never changes the exit code.
  - A new step script, `claims-check.sh`, has two modes, `pr` and `scheduled`.
  - `doc-spec-verify.yml` gains a `claims` job (no AI) on every same-repository PR: `claims validate --all`, `claims run --all`, and `claims attest --final` for each plan the PR touches. Findings fail the job. The job runs the PR's own adapters, so its checkout keeps no git credentials (`persist-credentials: false`). A PR that deletes a `docs/spec-claims/` its base has is a finding. With `doc-pr-release` installed, the amendment batch goes into a `spec-claims` section at the top of the PR description.
  - `doc-freshness-schedule.yml` gains a claims step: `claims run --all --scheduled`, `claims promote --reverify --all` and `claims validate --all`. Its findings keep the audit issue open under `### Spec claims`, with the week's judge sample.
  - `update-pr-body.sh` takes `DOC_SUPERPOWERS_SECTION=<name>`, which edits a named managed section, inserted at the top of the body when new.
  - The installer ships a helper directory only for a workflow that names a path in it that no `hashFiles(…)` guard covers. So installing `doc-spec-verify` alone does not ship the `doc-pr-release` helpers.
- **Requirements.** The checker needs bash ≥ 3.2, `jq` ≥ 1.6 and git, as the rest of doc-tools does. ### Changed (claims-enabled projects only)
- **`spec-inject --phase=plan` injects the gates.** Each chunk gets a `Claims gate (chunk N)` task before its spec-update task, and the last chunk gets a `Final claims gate` before the finalize tasks. ## v3.1.0 (2026-09-29)

This release adds two index operations that consumer repositories adopting v3 had to write for themselves. `move-entry` now repoints every entry that cites the moved doc (#22), and the new read-only `audit-merges` finds merges that silently lost an index change (#25). Both came out of abundance-mvp's v3 adoption, which had to carry local scripts for each: the hand-rolled copy of plugin logic this release makes unnecessary.

### Features
- **`move-entry` repoints other entries' `code_refs` and `code_oids`** (`scripts/doc-tools.sh`, #22). Before this, `move-entry` repointed only `replaces` / `superseded_by`. Every doc citing the moved one in `code_refs` kept pointing at a path that no longer exists. The only fix was a `set-code-refs` per citing entry, which recorded the new ref as `missing` (it did not exist at the doc's baseline) and left the doc stale until someone re-verified it.
  - A citing entry's `code_refs` is now rewritten in place, in order. A moved ref is dropped when the list already names its new path or has just gained it (so `[a, a]` becomes `[b]`); a duplicate of a ref the move did not touch stays.
  - Its `code_oids` key moves with the ref and keeps its recorded object id. A rename keeps the blob, so once the judged tree holds the rename, the citing doc reads as it did; a rename plus an edit reads stale, as it should.
  - When an entry also records the new path as a ref of its own, that ref's id wins.
  - The batch form is one simultaneous rename, so a chain `a→b, b→c` maps each cited path once.
  - An entry written before schema 3 (no `code_oids`) gets its refs repointed and, once the rename is committed, reads stale until `update-index` re-verifies it.
  - The report lists the repointed entries: each entry whose `code_refs` or `code_oids` named a moved path.
- **Parallel moves merge cleanly** (`scripts/merge-doc-index.sh`, #22). The repoint makes two branches that each move a different doc cited by one entry change that entry while `last_verified` ties, which the per-field rule turned into a conflict. The driver now merges both-sides `code_refs` changes as in-place substitutions: position by position when both sides kept the base's length, or one side's substitutions (a repoint) applied to the other side's list, collapsing as `move-entry` would. It takes that result only when it holds exactly the refs a three-way set merge keeps and makes no duplicate neither side had, so a remove plus an add at one position (two `set-code-refs` edits) still conflicts, as does dropping the moved ref. It merges `code_oids` key by key, three-way, only when neither side re-verified the entry (`last_verified` is still the base's) and the two sides agree on `content_hash` and `code_commit`; two re-verifications that tie are still a conflict. When one side did re-verify, its whole `code_refs` list wins as before, so a repoint made on the other side is lost there: `set-code-refs` the doc to the new path, then `update-index`.
  - **Known conflict:** branch A moves doc `a` while branch B moves a doc that `a` cites. A's re-key is a delete plus an add to the driver and B changed the deleted entry, so the driver stops with `a: deleted on one side, changed on the other` and leaves git's line-level merge of the file (v3.0.0 merged it and left `a2` citing the old path). Usually the only hunk is `generated_at`, and the lines of `a2` already carry B's new path. When the entries' own lines conflict too (a same-second write), take from each hunk the lines that name the moved docs' new paths. Then `check-freshness`: every doc reads as it did. A rename-aware merge for this shape is #33.
- **`audit-merges <since> [<until>]`, a read-only replay of index merges** (`scripts/doc-tools.sh`, #25). For every two-parent merge commit in the range whose parents' indexes differ, it works out what the merge should have recorded — the changed side's index when only one side changed it (git's file-level rule), otherwise the plugin's own merge driver run as an oracle — and compares that with the index the merge recorded, entry by entry. A stored `current` / `stale` status and the top-level fields are not compared. It reports, as JSON:
  - `"kept": "parent 1"` or `"parent 2"`: the merge kept one parent's whole entry where the three-way merge keeps the other parent's change. That is a silent revert, the shape a driver that is not base-aware (v2's) produces on a `last_verified` tie.
  - `"neither"`: the merge commit itself rewrote the entry, usually a re-verification while resolving.
  - `refused`: a merge that needed a resolution the driver would not make. It stays reported after a correct hand resolution.
  - `unreadable`: `"recorded"` when the merge's own index is not exactly one index object, `"parent 1"` / `"parent 2"` when the only side that changed the index, whose index the merge was to take, is not. An unreadable parent that the other side repaired is no finding.

  An octopus merge is listed under `skipped`. The replay uses one merge base, so a criss-cross merge is approximated. It needs `merge-doc-index.sh` beside it, so a vendored `doc-tools.sh` exits 1.

  It exits 1 on any finding. Run over the 315 merges on abundance-mvp's `main` since 2026-09-09 (278 of them with differing parent indexes, 128 needing the driver), it found 11 reverted entries (a v2-driver `git fixmerge` undoing `main`'s `code_refs: [""] → []` normalisation), 38 merge-commit rewrites and 1 merge the driver would refuse (a doc deleted on one side and changed on the other).

## v3.0.1 (2026-09-29)

A patch release that keeps the Claude Code hooks' reports readable at any size, and stops a slow check from silently switching the gate off. Claude Code keeps each hook string (`systemMessage`, `additionalContext`, the stderr of a blocking exit 2) inline only up to 10,000 characters; past that, Claude gets a 2,000-character preview of a saved file (https://code.claude.com/docs/en/hooks). In v3.0.0 every list the three Claude hooks built was unbounded, so a commit that staled about 140 docs lost most of its report. Reported from abundance-mvp (`docs/issues/2026-09-29-doc-superpowers-hook-output-uncapped-10k-limit.md`).

**Upgrading:** re-run `install.sh install --claude` in each repository that has the Claude tier. It adds `.claude/hooks/doc-superpowers/hook-lib.sh`, which the hooks now source. Until then, `status` reads `outdated`. **If you set `DOC_SUPERPOWERS_STRICT=1`:** a gate check that runs past its 7 s budget now blocks the commit, where v3.0.0's hook was killed at its timeout and let the commit through. On a large index (see *Known issues*), expect that when a commit touches code many docs cite, and bypass it with `DOC_SUPERPOWERS_SKIP=1`.

### Fixes
- **Every Claude hook string stays under 10,000 characters** (`scripts/hooks/claude/hook-lib.sh`, new; `pre-commit-gate.sh`, `post-commit-sync.sh`, `session-summary.sh`) — The three hooks' copies of `_emit` are now one sourced library, so their bounds cannot drift apart.
  - A one-line summary names the first 10 paths of each list; a report section lists 15 docs; a doc shows 3 of its changed refs. Each list is also held to 2,500 characters. Then comes `…and N more (run 'doc-tools.sh check-freshness' for the full list)`, so every section keeps its count line whatever the stale count. The gate's pointer is to `check-freshness --tree $(git write-tree)`, the staged tree it judged.
  - As a backstop, `_emit` and the STRICT gate's stderr cut each string at 9,000 characters, at a line end, with the same pointer. The gate keeps room for its `Commit blocked …` line. The cut splits on newlines rather than using `rindex`, which counts bytes in jq 1.6.
  - The hooks split their report with `read`, not `${report%%…}`, which bash runs in quadratic time. On a 1,000-doc report the v3.0.0 gate and post-commit-sync hooks ran for minutes, so Claude Code would have killed them at their 10 s timeout, and they showed nothing.
- **The gate and post-commit-sync run their check under a watchdog** (`pre-commit-gate.sh`, `post-commit-sync.sh`, `hook-lib.sh`) — All three hooks are registered with `timeout: 10`, but only `session-summary.sh` had a watchdog. A hook Claude Code times out blocks nothing, so under `DOC_SUPERPOWERS_STRICT=1` a slow check let the commit through and said nothing.
  - The gate and post-commit-sync now give the check 7 s (session-summary keeps its 2 s). The check runs in its own process group, which is killed as a whole past the budget. The hook then says `doc-superpowers: check skipped (budget): …` as a `systemMessage`, and the gate also tells Claude in `additionalContext`.
  - **Under STRICT, a gate check that runs out of time blocks** (exit 2, the reason and the `DOC_SUPERPOWERS_SKIP=1` bypass on stderr), as a check that cannot run already did.
  - A failed check's reason now comes from that run's stderr: the gate's scoped and whole-index runs each keep their own. The gate and post-commit-sync used to run a failed check a second time to get it.
- **A hook without its library says so** (`pre-commit-gate.sh`, `post-commit-sync.sh`, `session-summary.sh`, `scripts/hooks/install.sh`) — The library is sourced only once a hook knows it has work (doc-tools and the doc-index present, not QUIET), by an absolute path. If `hook-lib.sh` is missing then, a hook emits a one-line `systemMessage` saying to re-run `install --claude`, and the STRICT gate blocks. `install --claude` writes the library before the hooks, and `uninstall --claude` removes it. `status` flags a hook whose library is missing or belongs to another version.

### Tests
- **The hooks' real output is measured** (`scripts/test-hooks.sh`) — A new section drives the installed hooks through their registered commands on a 1,000-stale-doc report: long paths, 40 changed refs per doc, 300 missing docs, and 150 of those on disk. For each hook and each field it emits (`systemMessage`, `additionalContext`, the STRICT stderr), it asserts that the field is shorter than 10,000 characters, holds the counts and the full-list pointer, and that stdout is valid JSON. That report comes from a stub `doc-tools.sh`, because a real check of 1,000 docs takes far longer than any hook's budget. A second test runs the real `doc-tools.sh` on 41 stale docs and checks the `…and N more` lines. Written first: against v3.0.0, 73 of the new assertions failed. The largest string was a 185,218-character `systemMessage`, and the gate and post-commit-sync never finished.

With a `doc-tools.sh` that never finishes, the gate and post-commit-sync return before that timeout, say `check skipped (budget)`, and kill the check's children. The STRICT gate blocks. A shimmed `sleep` shows that neither hook holds its output open for the watchdog.
- **Every Claude hook run is held to the contract** — `run_claude_hook` now checks, on every run, that the exit code is 0, or 2 only when `DOC_SUPERPOWERS_STRICT=1` was set (a bash syntax error also exits 2, and a PreToolUse exit 2 blocks the commit), and that stdout is one JSON object or nothing. A breach fails the test that ran the hook. The suite ends with the tally.

## v3.0.0 (2026-09-28)

A major release in which every layer of doc-superpowers now reports what is actually true. It is the whole of sweep 05ea982. A full-repository audit of v2.15.0 (`docs/plans/2026-09-27-full-repo-05ea982-audit-findings.md`) found one P0 and grouped its findings into 14 cluster issues (`docs/issues/2026-09-27-sweep-05ea982-I01…I14-*.md`), each fixed test-first as one Task (T1–T14). A five-seat whole-branch review and its fix wave followed, then a fresh audit → update → diagram pass over the living docs: 57 commits in all.

The biggest change is the freshness model. A doc is stale when the *content* of the code it cites differs from what was verified, not when a commit id differs. So squash merges, rebase-merges, cherry-picks, reverts and shallow clones no longer read stale, and the commit that verifies a doc no longer leaves it stale. Around that model:
- the index has one locked, atomic writer;
- the merge driver is a real three-way merge;
- the Claude hooks run at all (v2's read an environment variable Claude Code never sets);
- the CI gates fail closed, and the AI templates can actually run;
- the release-fragment pipeline no longer loses text.

It is a major version because a v2 script or workflow can notice five changes: the index schema, the installer's defaults, the CI template set, the manifest set and several verbs' exit codes. Closes #5 and #18.

**Upgrading:** follow README.md → *Upgrading from 2.x* in every repository that has doc-superpowers installed. Its first step, re-running every installed tier, is what replaces the v2 hooks, the pinned merge-driver registration and the vendored `.github/scripts/` copies.

### Breaking Changes
- **Index schema v3: freshness is decided by content (`code_oids`)** (`scripts/doc-tools.sh`, `docs/.doc-index.json`, `references/doc-spec.md`) — For each code ref, writers record the git object id of its content in `code_oids`: a blob, a tree, a submodule's commit, or `missing`. Readers compare these with HEAD, or with `--tree <tree-ish>`, in one `git cat-file --batch-check`.
  - **Upgrade path.** A v2 index is read as it is, with no migration step, and a no-op leaves it byte-identical. The first real write stamps `schema_version: 3` and drops a pre-v2 `version` key. A v2 entry keeps the old commit comparison until `update-index` re-verifies it.
  - **What a script reading the index or the JSON output will see:**
    - once re-verified, `code_refs` are literal paths, not git pathspecs, and a glob-looking ref warns when written;
    - `commits_behind` is computed for stale docs only, and is `null`, never a masked `0`, when `code_commit` is not an ancestor of HEAD here (a deleted squash-merged branch, a shallow clone, a cherry-picked verification);
    - in a shallow clone, writers store `code_commit: null`, with a warning;
    - stored `status` is only `deprecated` or absent: the first write drops a legacy `current` / `stale`, so compute the state with `check-freshness` / `status`;
    - `last_verified` is `null` after `build-index` and `add-entry`;
    - the generated-doc marker is `<!-- Generated by doc-superpowers -->`, without date and commit; older markers are still recognized.
- **Record docs are never reported stale, decided by `doc_type`** (`scripts/doc-tools.sh`, `references/doc-spec.md`, `docs/conventions.md`) — A record describes a point in time: an entry whose `doc_type` is `plan`, `issue`, `audit` or `design-spec`, or whose path is under `docs/archive/`.
  - `check-freshness` and `status` report a record `current`, with `"record": true` and `commits_behind: null`, and never look up its refs. A missing record still reads `missing`, and a deprecated one `deprecated`.
  - There is no new status value, so consumers that count `stale` / `current` need no change, but their counts will change: in this repository, records were 91% of the stale signal.
  - v2 indexes often typed design specs `spec`. Retype them with the new `doc-tools.sh set-doc-type <doc> design-spec`, never with `remove-entry` + `add-entry`, which drops the entry's verification, deprecation and links. `set-doc-type` accepts a documented type or one the index already uses; anything else exits 1 and writes nothing.
- **`doc-tools.sh` exit codes and refusals** (`scripts/doc-tools.sh`) —
  - **Usage errors exit 2 everywhere:** no subcommand or an unknown one (was 1), an unknown option, an option without its value, the wrong number of arguments, a repository verb outside a git work tree.
  - **Run from the repository's top level.** Below it, the index verbs (`build-index`, `check-freshness`, `status`, `update-index`, `add-entry`, `remove-entry`, `move-entry`, `set-code-refs`, `set-doc-type`, `deprecate-entry`) and `fragments merge` exit 2; they used to write a stray `sub/docs/.doc-index.json`. `bump-version` / `check-version` exit 1 there.
  - **A path not in the index.** `deprecate-entry` and `update-index` report it, apply the rest, then exit 1. `deprecate-entry` used to skip it with exit 0 (so `deprecate-entry <old>` after a `move-entry` was a silent no-op), and `update-index` used to abort the whole batch. `remove-entry` stays idempotent (SKIP, exit 0).
  - **A broken index.** A 0-byte or malformed index makes every index-reading verb exit 1; v2 read it as an empty index. Every writer refuses a symlinked index.
  - **Per verb.** `build-index` refuses to replace a non-empty index without `--force`, refuses empty input, and keeps the first line of a duplicate key (v2 kept the last). `check-freshness` rejects positional arguments, and an empty `--code-refs` value matches nothing. `fragments merge` exits 3 when it refuses (last bullet); `fragments validate` exits 2 for a symlink. `implementation-status --filter` is removed. `set-implementation` exits 1 when a doc has no metadata paragraph to anchor a new block, and 2 for a multi-line `--ref` / `--note`. `check-version` fails on a pre-release first heading or zero manifests. `jq` ≥ 1.6 is checked up front.
  - **Newly documented here:** an unreadable indexed doc aborts the whole `check-freshness` run (exit 1, `ERROR: cannot hash <doc>`) instead of reporting the others.
- **Installer defaults: `--ci` no longer installs every AI workflow, and the Claude tier is per-user** (`scripts/hooks/install.sh`, `scripts/hooks/state.sh`) —
  - **CI tier.** A first `install --ci` installs only the two shell workflows, `doc-freshness-pr` and `doc-freshness-schedule`; each Claude-powered workflow is opt-in by name (`--workflows=…` or `all`). After that, a plain `install --ci` reproduces the recorded workflow set, base branch, cron and strict setting, kept in `.claude/doc-superpowers/installed.json` (schema 2; commit it). `--ci-strict=false` is new.
  - **Upgrading a v2 CI tier.** A pre-3.0 install's choices are read back from its workflows, so a v2 repository that got every AI workflow by default keeps them. Remove the ones you did not choose with `install.sh uninstall --ci --workflows=<names>`.
  - **Claude tier.** `.claude/settings.local.json` and `.claude/hooks/doc-superpowers/` go in git's `info/exclude`, and the registered commands run `"$CLAUDE_PROJECT_DIR"/.claude/hooks/…`. A repository that tracks those files must untrack them. Pulling that commit deletes them from every other clone, so each teammate re-runs `install --claude` (README step 4).
  - **Git hooks** go only where git runs them (`git rev-parse --git-path hooks`: worktrees, submodules, subdirectories). A `.githooks/` that `core.hooksPath` does not name is no longer used, and a global or system `core.hooksPath` is refused.
  - **Uninstall** removes only files byte-identical to the plugin's copies, so re-install before you uninstall.
  - **Command line.** A flag outside a command's scope exits 2, `uninstall --workflows=<typo>` exits 1, `install.sh help` exits 0, and `status` takes tier filters and needs a git work tree. `--helpers` is deprecated and inert; `--helpers=false` is refused (exit 1, nothing written) while `doc-pr-release` is selected or installed.
- **`doc-index-update` is retired** (`scripts/hooks/ci/`, `scripts/hooks/install.sh`) — It fed every changed `docs/` path (the index and PNGs included) to `update-index`, which exited 1 on all 12 recent `main` commits replayed; when it succeeded, it took "doc edited on main" as "doc re-verified". The template and its `--workflows` name are gone (`install --workflows=doc-index-update` exits 1). Any `install --ci` removes an installed copy carrying the workflow marker and drops its state entry; an unmarked file of that name is kept and reported. Eight CI templates remain.
- **The Claude hooks read their input from stdin** (`scripts/hooks/claude/`) — v2's gate and sync hooks read `$TOOL_INPUT` and the JSON path `.command`. Claude Code sets neither, so through their registered command they never activated, and `DOC_SUPERPOWERS_STRICT` never blocked a commit. Now:
  - they read the event JSON on stdin (`.tool_input.command`) and answer through `hookSpecificOutput.additionalContext` / `systemMessage`;
  - a STRICT block exits 2 with its reason on stderr, which `DOC_SUPERPOWERS_QUIET` no longer hides;
  - the gate matches `git commit` only in command position, and hands a command that stages as it commits (`git add … && git commit`, `commit -a`, a pathspec) to the git pre-commit hook;
  - no hook writes the index (the dead `update-index` calls are gone: a working one would have attested docs nobody read), and the `DOC_INDEX` override is gone.

  A v2 Claude tier runs the old scripts until `install --claude` is re-run; `install.sh status` marks it `outdated`.
- **Merge-driver registration, and conflicts where v2 guessed** (`scripts/merge-doc-index.sh`, `scripts/hooks/install.sh`) — v2 registered the driver by an unquoted path pinned to one version, so a space in it or a pruned plugin version gave a conflict with no markers. v3 registers a quoted command that finds the newest driver at merge time; re-run `install --git` (until then `status` flags the pinned registration). Where v2 silently kept one side, the driver now conflicts: markers in the index, exit 1, each key and field named on stderr (see *Features*).
- **CI templates fail closed; the AI ones need a tag, a repository setting and current step scripts** (`scripts/hooks/ci/*.yml`, `scripts/hooks/ci/doc-superpowers-steps/`) —
  - **Freshness workflows.** A check that cannot run is no longer "0 stale". The PR check warns (`::error::` and a failed check under `--ci-strict`); the scheduled run fails and never closes its issue on it. Missing docs count along with stale ones.
  - **Plugin version.** The AI templates install the plugin from the GitHub tag `v<installed version>`, so they run only once that tag is pushed.
  - **Triggers.** The AI templates run for same-repository PRs only (no forks, no Dependabot). `workflow_dispatch` is removed from `doc-review-pr`, `doc-spec-verify` and `doc-pr-full-cycle`. Hard-coded path filters are replaced by an in-job scope check against the doc index.
  - **`doc-release`** commits to `doc-superpowers/release-notes-<run_id>-<run_attempt>` and opens a PR, which needs the setting *Allow GitHub Actions to create and approve pull requests*.
  - **Step scripts.** Step bodies moved into `.github/scripts/doc-superpowers-steps/` and run from the checkout. For `doc-pr-release` that is the PR head, including the step that receives the Anthropic secrets. A PR branch cut before the upgraded scripts reached its base lacks them, so `doc-pr-release` fails there until the branch is updated.
  - **No check runs on bot commits.** Commits and PRs made with the job's token start no workflow run, so required checks on them wait at "Expected" until the author pushes again or closes and reopens the PR.
- **`claude-code.json` removed; Cursor's install path moved** (`claude-code.json`, `scripts/doc-tools.sh`, `.cursor-plugin/`) — No client read `claude-code.json`. `bump-version` / `check-version` manage five manifests and no longer look for it, and `doc-release`'s commit step no longer accepts it; a project that keeps one bumps it itself. Cursor's manifest points at `./skills/`, and the manual install path is `~/.cursor/plugins/local/doc-superpowers`: move a clone in `~/.cursor/plugins/doc-superpowers`.
- **Release fragments: one consumption rule** (`scripts/doc-tools.sh`, `scripts/hooks/ci/doc-pr-release/RELEASE-NOTES.next.README.md`, `references/release.md`) —
  - **Range.** `fragments merge <range-start> <range-end>` treats a fragment as unreleased while it is present at `<range-end>`, including one merged after a release branch was cut. v2's `--from=<tag>~1` advice is withdrawn: pass the previous release's tag, or `ROOT` for a first release. Both refs are validated.
  - **Refusal.** While an earlier release's commit has not reached `<range-end>`, the fragments it consumed are still present, and `fragments merge` exits 3. The release commit must reach `main`.
  - **Old README copies.** An existing `RELEASE-NOTES.next/README.md` is never overwritten, so a v2 copy keeps giving v2 advice; `doc-tools.sh tools status` reports when it differs from the plugin's.

### Features
- **Content-based freshness and staged-tree checks** (`scripts/doc-tools.sh`) — `check-freshness --tree "$(git write-tree)"` judges the commit being made, reading the index, the docs and the code refs from that one tree. Also:
  - `--code-refs-from <file|->` takes a newline- or NUL-separated list without argv limits, e.g. `git diff -z --name-only --no-renames <range> | doc-tools.sh check-freshness --code-refs-from -`;
  - `--code-refs` matches whole path segments (`src/m1` no longer matches `src/m10`);
  - `code_refs_changed` lists exactly the refs whose content differs, and a submodule bump reads stale;
  - the index file is left out of any ref that covers it (`docs/`, `.`);
  - writers name untracked files under a ref: their content is recorded but HEAD lacks it, so the doc reads stale until they are committed or ignored.

  On 2,000 docs × 503 commits with 60 stale, `check-freshness` went from 43.0 s to 1.1 s (bash 5) and 61 s to 1.7 s (bash 3.2), and from 4,062 git processes to 7.
- **Only `update-index` attests** (`scripts/doc-tools.sh`) — Writing an entry no longer claims someone verified the doc.
  - `update-index` is the one verb that writes `last_verified`. Its report distinguishes `Refreshed`, `Re-verified` (a real write) and `Unchanged`, and it keeps a deprecation (v2 silently un-deprecated).
  - `build-index` and `add-entry` take each entry's baseline from the doc's own last commit (one `git log --stdin` walk), never HEAD; a never-committed doc takes the working tree.
  - `build-index --force` re-records every entry unverified, keeping only each re-indexed key's deprecation, `superseded_by` and `replaces`.
  - `deprecate-entry` no longer bumps `last_verified`, and `--superseded-by X` sets `X.replaces` when it is empty.
- **New index verbs: `set-code-refs`, `set-doc-type`, `move-entry --stdin`** (`scripts/doc-tools.sh`) — 16 subcommands (14 in v2.15.0).
  - `set-code-refs <doc> --refs a,b` (closes #18) edits an entry's refs in place, keeping its key position and every other field. A kept ref keeps its recorded content; a new one is recorded as `add-entry` records it. The stored `code_commit` is never newer than any ref's recorded content, so `commits_behind` can over-count but never shows a masked 0.
  - `set-doc-type <doc> <type>` retypes an entry in place.
  - `move-entry --stdin` reads `<old><TAB><new>` pairs, checks every pair before writing anything, and applies them as one simultaneous rename, so chains and swaps work (PR #16's Option A).

  Archiving is `git mv` + `move-entry` + `deprecate-entry <new path>`, with no `archived_at` field.
- **One locked, atomic index writer** (`scripts/doc-tools.sh`) — Every write takes a `mkdir` lock (`docs/.doc-index.json.lock`, owner pid recorded, `DOC_TOOLS_LOCK_TIMEOUT`, default 30 s), reads one validated snapshot, runs one jq pass, and moves a temp file into place with the prior mode (0644 when new).
  - A dead owner's lock is broken; an owner that is alive but another user's is waited on.
  - A no-op writes nothing, not even `generated_at`, and reports list only changed keys.
  - INT exits 130 and TERM 143, never resuming, and a fatal error under bash 3.2 exits 1 (was 0).

  Measured: 10 parallel `update-index` runs lost 9 updates, now none; a racing reader found the index unparsable in 55 of 214 reads, now none; `update-index` of 50 docs on a 4,000-entry index went from 9.2–10.5 s to 0.32–0.41 s.
- **One command-line grammar** (`scripts/doc-tools.sh`) — One verb table generates both the dispatcher and `--help`. Options go anywhere, as `--opt VALUE` or `--opt=VALUE`, and `--` ends them. `--help`, `-h` and `help` exit 0 anywhere, without jq or git. One mapping-line parser strips CR, trims refs, rejects a bare path or an ambiguous `:` path, and warns about a ref that matches no tracked file. Git failures are checked instead of read as "no history", and `log.showSignature` is pinned off.
- **A real three-way merge driver** (`scripts/merge-doc-index.sh`) — Each key is merged against the base:
  - one side's change beats an unchanged side, and delete against modify conflicts;
  - fields merge one by one; the verification record (`content_hash`, `code_oids`, `code_commit`, `last_verified`) moves as a unit, and `deprecated` wins;
  - when both sides changed a field and `last_verified` does not order them, it conflicts instead of picking ours;
  - the top level starts from ours, so `schema_version` and unknown fields survive, and key order is kept;
  - each side is validated, and a signal leaves conflict markers, never a half-written file.

  `test-merge-driver.sh` went from 19 to 486 assertions, using the real verbs, merged, rebased and reverted in both directions.
- **Hooks that judge the commit being made** (`scripts/hooks/git/`, `scripts/hooks/claude/`) —
  - **pre-commit** checks the staged tree, so the commit that makes a doc stale is the one reported (blocked under STRICT), and judges every entry the staged index adds. An indexed doc the commit leaves out is "not in this commit" (`git add` it) when it is on disk, and "missing from disk", with `move-entry` advice, when it is gone.
  - **prepare-commit-msg** acts only on editor commits, so `-m`, `-F` and `--amend --no-edit` never commit `#` lines.
  - **pre-push** reads the refs being pushed; **post-merge** and **post-checkout** diff with `--no-renames`, so a moved file's old path is in scope; **post-commit-sync** handles a root commit.
  - **Stop** is scoped to working-tree changes, with a 2 s process-group watchdog that never holds stdout.
  - In every hook, missing tooling is silent, and failing tooling prints one line and blocks only under STRICT.
- **An installer that owns exactly what it wrote** (`scripts/hooks/install.sh`, `scripts/hooks/state.sh`, `scripts/doc-tools.sh`) — Every check runs before the first write, and nothing is written through a symbolic link.
  - Integration into your own hook is one POSIX block after its `#!` line, passing `"$@"`, pre-push's stdin and pre-commit's exit code; uninstall restores the hook byte for byte.
  - In settings, only entries that run the installer's scripts are touched. `.gitattributes` and `info/exclude` get marked blocks, and an unreadable `installed.json` is refused, never overwritten.
  - `status` reports `outdated` for a hook, an integrated copy, a Claude script or a settings command that differs from what this version writes.
  - Hooks find `doc-tools.sh` by numeric version: no GNU `sort -V`, never a sibling directory without a version name.
- **Bounded, runnable AI jobs** (`scripts/hooks/ci/*.yml`, `scripts/hooks/ci/doc-superpowers-steps/`) —
  - Every `claude-code-action` step passes `github_token: ${{ github.token }}` (closes #5 without `id-token: write`), and agents get a scoped `--allowedTools`, `--max-turns` and `timeout-minutes`.
  - **The agent never commits.** `commit-changes.sh` checks the changed paths against the workflow's set, with a pre-agent copy of the checker and git hooks and fsmonitor off, then commits and pushes without force. It is an integrity check against agent mistakes, not a sandbox.
  - Writers share one non-cancelling concurrency group per branch (`queue: max`). A superseded `doc-audit-update` or `doc-pr-release` run ends green; `doc-pr-full-cycle`, which nothing would re-run, fails and asks for a re-run.
  - `doc-review-pr` is split into a fixed-prompt PR job and a tag-mode `@claude` job for members, and `doc-pr-release` refuses a fork PR's number on `workflow_dispatch`.
  - Freshness results stay in `$RUNNER_TEMP` files, and only counts reach step outputs (v2 hit E2BIG at about 421 docs). One PR comment is upserted by marker and bot author, and updated to "none" once the PR is clean.
- **Release fragments: a lossless consumer and a force-push-safe producer** (`scripts/doc-tools.sh`, `scripts/hooks/ci/doc-pr-release/`, `scripts/hooks/ci/doc-pr-release.yml`, `references/release.md`) —
  - **Consumer.** Each fragment is merged without loss, or skipped with a warning and kept for the next release. Units are deduplicated, prose and wrapped lines stay with their note, and sections fold onto one vocabulary. `--paths-out F` / `=F` is supported, and the new `--remove` `git rm`s exactly the consumed fragments. `fragments list` is linear, never aborts silently, and adds `no_notes` / `problem` fields.
  - **Producer.** The workflow seals the fragment (the agent computes no hash). `commit-and-push.sh` commits only the fragment and pushes with a compare-and-swap: someone else's push supersedes the run, and a force-push is never undone. A hand-edited fragment is never overwritten or re-sealed, one the release would skip is refused, and `<!-- doc-superpowers:no-notes -->` is an explicit state.
  - **Helpers.** `extract-context.sh` excludes base-branch and bot commits; `update-pr-body.sh` ignores markers inside code fences and refuses an append into an unclosed fence.
  - **`/doc-superpowers release`** merges fragments before drafting and commits before tagging. Its range starts at the latest version's tag, else the commit that added that version's heading (an untagged release), else the nearest `v*` tag, else `ROOT`.
- **Implementation, version and vendoring verbs without GNU sed or ripgrep** (`scripts/doc-tools.sh`, `references/doc-spec.md`) —
  - `set-implementation` is one awk pass (values through `ENVIRON`, literal matching, a temp file moved into place with the doc's mode), and creates the block after a `**Date**:`, `**Date:**` or `**Created**:` paragraph.
  - `set-implementation`, `implementation-status` and `update-index` share one block grammar: `Realized-by:`, entries at any indent, wrapped lines, `[]`, fenced examples ignored.
  - `bump-version` is all-or-nothing and keeps file modes; the new `tools version` reports the plugin's version. `tools uninstall` keeps edited or foreign files, and `tools install` leaves every vendored script executable.
  - GNU sed and ripgrep are no longer needed; mawk must be ≥ 1.3.4.
- **The skill prompt matches the tools** (`skills/doc-superpowers/SKILL.md`, `references/`, `evals/`) —
  - Tools resolve from `${CLAUDE_SKILL_DIR}/../..` in every client, with the plugin cache as a fallback; a tool that cannot be found stops the run.
  - Index writes follow one routing table. `sync` adds untracked docs, and for a missing one asks the commit that removed it whether it was a rename (`move-entry`) or a deletion (`remove-entry`).
  - `review-pr` takes its base from `origin/HEAD` or `origin/main`, and stops on a missing base or an empty diff.
  - Safety Rules set a trust boundary: no secrets, confirmation before moving docs, and no repository scripts run.
  - `update` takes `--report=<path>` and archives the report it applied. In CI, `update` and `sync` report what CLAUDE.md or README.md need instead of editing them.
  - Generated docs keep their Mermaid source under each PNG. The `:amends` landed-check reads the whole `AMENDED` block, so blocks in the 2.x layout still pass.
  - The `release` and `hooks` bodies moved to `references/release.md` and `references/hooks.md`. Evals went from 13 to 20, with machine-checkable fields and fixtures the suite builds.
- **Cross-client packaging** (`.opencode/plugins/doc-superpowers.js`, `GEMINI.md`, `references/tool-mappings.md`, `.codex/INSTALL.md`) — The OpenCode plugin appends the tool mapping to OpenCode's system-prompt array; v2 replaced the array with a string, so the mapping never reached the model. `GEMINI.md` no longer imports SKILL.md into every session (about 11k always-on tokens saved). `references/tool-mappings.md` is the one capability matrix, with corrected OpenCode, Codex and Gemini tool names, and the Codex snippet is a `[features]` table.

### Fixes
- **Security: symlinked writes, a sibling directory's script, sed injection, PR code** (`scripts/hooks/install.sh`, `scripts/hooks/state.sh`, `scripts/doc-tools.sh`, the hook templates, `skills/doc-superpowers/SKILL.md`) —
  - The installer and `tools install` followed committed symlinks: `.githooks/pre-commit → ~/.bashrc` gave a hostile clone persistent code execution once its owner ran the installer.
  - Hooks resolved the tool as `*/scripts/doc-tools.sh | sort -V | tail -1`, running whichever sibling directory's script sorted last.
  - `set-implementation` spliced `--ref` / `--note` / `--status` into `grep -E` and GNU `sed` program text, allowing sed `e` / `w` injection and corrupting ordinary values such as `R&D` or `(squash)`.
  - Discovery ran `uv run scripts/validate_docs.py` from the working tree, so `review-pr` on a checked-out PR executed the PR author's code.

  All four are gone; the skill never runs repository scripts.
- **Index data loss** (`scripts/doc-tools.sh`) — Six writers each did an unlocked read-modify-write, and five truncated the index with `>`. Parallel `update-index` runs (which the `update` action dispatches) lost updates while every run exited 0. Overlapping writes left an unparsable index, which the hooks read as "tooling absent". A TERM mid-`build-index` exited 0 with a truncated index, and writes left the index at mode 0600.
- **Wrong freshness verdicts** (`scripts/doc-tools.sh`) — `check-freshness` carried its own tab-separated copy of the freshness logic, so an empty middle field shifted the columns and reported stale docs as current. `log.showSignature` leaked into `code_commit`, and a stored `code_commit` reached git without being checked as an object id.
- **The merge driver lost changes** (`scripts/merge-doc-index.sh`) — It used the base only in `has()` checks and kept the whole entry with the newer `last_verified`. Measured through real git: a re-verify undid a deprecation, a `move-entry` repoint was lost, reverting a deprecation did not revert it, and merge and rebase lost different data. It also wrote `version: 0` and dropped `schema_version`, and a 0-byte "theirs" deleted every base entry with exit 0.
- **Hooks and installer** (`scripts/hooks/`) — STRICT blocked with an empty stderr, and `prepare-commit-msg` committed `#` lines under `-m` (28 of this repository's own commit messages carry them). The bash-only integration block failed under `/bin/sh`, dropped `"$@"` and swallowed STRICT. The Claude settings merge deleted user hooks that shared a hook group with ours. A plain re-install flipped STRICT off and installed all nine workflows, and a malformed `installed.json` brought back workflows removed on purpose.
- **CI** (`scripts/hooks/ci/`, this repository's `.github/`) — A tool failure read as `stale_count=0`, and the schedule job closed its issue. The six AI templates ran `claude-code-action` with no `plugins` and no `claude_args`, so the model had neither the skill nor Bash/Write tools (read from the action's pinned source). Any member comment on `doc-review-pr` ran a paid review of the default branch. This repository's own freshness workflows called a `doc-tools.sh` that was never committed, failing open since 2026-04-05.
- **Release fragments** (`scripts/doc-tools.sh`, `scripts/hooks/ci/doc-pr-release/`) — A fragment's last line was dropped without a trailing newline, yet the fragment was still listed for deletion, and text outside a `###` heading was discarded. A fragment merged after a release branch was cut read as released. `commit-and-push.sh` could undo a force-push and swept already-staged files into its commit. `extract-context.sh` leaked base commits after "Update branch", and died at the 128 KiB per-argument limit.
- **Implementation and version verbs** (`scripts/doc-tools.sh`, `scripts/hooks/install.sh`) — `set-implementation` anchored on `**Date:**` while the templates use `**Date**:`, exiting 0 with the file unchanged, and its writer and two readers parsed different grammars, dropping `Realized-by:` entries from the index. `bump-version` half-applied on a malformed manifest, both version verbs passed on zero manifests, and `tools uninstall` ran `rm -rf` on user-added files.
- **Prompt layer** (`skills/doc-superpowers/SKILL.md`, `references/spec-lifecycle-actions.md`) — `$DOC_TOOLS`, the installer and `references/` resolved only through Claude Code's plugin-cache glob, so 4 of the 5 supported clients had no tooling. In `review-pr`, `|| echo main` bound to `sed`, so the base was empty wherever `origin/HEAD` is unset and the scoped check applied no filter. ## v2.15.0 (2026-09-01)

Adds a third `--specs` role, `:amends`, for a plan whose deliverable is correcting what a spec *says* without building its surface — status-neutral by construction and, unlike either existing role, **verified as landed**. Shipped as PR #17 (`feat/amends-spec-role`), including a review round that pinned one WARN literal, recorded the plan-time `Status` the finalize clause compares against, and made the injected task one-per-spec.

### Features
- **`:amends` — a third `--specs` role, for a spec whose text the work corrects without building its surface** (`references/spec-lifecycle-actions.md`, `references/spec-lifecycle-protocol.md`, `skills/doc-superpowers/SKILL.md`) — `--specs` recognised exactly two roles, **target** (advance it) and **constraint** (never touch it), and neither is true of a plan whose deliverable is *correcting what a spec says*. `target` is false — no surface is built, and it makes the spec eligible for an advancement it must not receive, which is issue #12's false-advancement re-entered by a different door. `constraint` is false in the other direction — a constraint is read-only by definition ("no `Status` change, no Implementation Notes, no `code_refs` refinement, no `update-index` call") and this work writes the spec. The gap that costs something is narrower: **nothing verified that a promised amendment landed.** `spec-verify`'s constraint branch skips the spec entirely; its target branch compares code against the spec's text, which is the wrong direction when the *text* is what was supposed to change. A plan could promise a correction, the executing agent skip the task, and the doc keep asserting the stale model with no check noticing — the same silent shape as #12, in reverse. `<path>:amends` is now explicit-only (inference cannot produce it: an amendment is a claim about what the work promised to write *in the spec*, which no code diff expresses), status-neutral by construction (R2/R3 hold exactly as for a constraint — no `Status`, no Implementation Notes, no `code_refs`), and **verified as landed**. The record is an inline dated `AMENDED YYYY-MM-DD` block in the corrected section citing the plan that wrote it, followed by `update-index` because the spec's bytes changed even though its status did not. Whole-doc supersession is untouched and remains a different operation: `Supersedes:` / `Superseded by:` replaces a document, an `AMENDED` block corrects a passage. The boundary is one sentence and it is the whole test: *a co-move of a value or line inside a spec the plan `implements` or `constrains` is not an amendment; `amends` is for a spec whose stated behaviour the plan changes and whose surface the plan does not build.*
- **The landed-check is a two-stage grep, and a bare block search is explicitly not sufficient** (`references/spec-lifecycle-actions.md`) — `spec-inject --phase=plan` appends a one `### Task N+1a: Land the spec amendment for {spec-path}` **per `:amends` spec per chunk** after that chunk's spec update task — the injector substitutes `{spec-path}`, `{plan-path}`, the performing task `{N}`, and a `Status at plan time: {status}` line it reads at inject time — plus an assertion in the finalize task (block present **and** cites the plan **and** `Status` still equals that recorded plan-time value). Its Step 2 runs `grep -n -A4 'AMENDED 20' <spec-path> | grep -F '<plan-path>'`, with the plan path substituted at inject time from `--plan=`. Both stages are load-bearing: the first finds a dated block, the second proves the block belongs to *this* plan. A bare `grep 'AMENDED 20'` passes vacuously on any spec that earlier work amended, so on its own it verifies nothing about the work in hand — it would report PASS on precisely the file a forgetful executor left untouched.
- **`spec-verify` accepts `--plan=<path>` in both modes, and degrades loudly without it** (`references/spec-lifecycle-actions.md`, `references/spec-lifecycle-protocol.md`) — post-execute and review mode both re-run the landed-check for every `:amends` spec. A missing or unattributed block is a FAIL in post-execute and a **P1 Amendment not landed** finding in review; amendment specs are exempt from the *status* half of the check at any value, and are excluded from the Specs → Code coverage axis (this work built none of their surface by definition, so "spec without implementation" is a meaningless verdict for them). When `--plan` is absent the citation stage cannot run: the check degrades to block-present and emits exactly `WARN: amendment citation unverified (no --plan)` — one literal on every path (post-execute, review, and the execute phase). A degraded check contributes a WARN, never a FAIL, and is **never** reported as a full pass — the point of the role is that a promised amendment is provable, so an unproven one has to say so.

## v2.14.0 (2026-07-29)

Adds `move-entry`, the missing doc-index operation for a doc that moved. Until now the only documented remedy for a renamed doc — the one five hook scripts and `update-index`'s own WARNING told you to run — was `remove-entry` followed by `add-entry`, which discards the very metadata staleness is derived from. The entry that comes out the other side reports `current` forever, no matter how far its code drifts: a doc-freshness tool silently reporting a doc as fresh is the one failure it exists to prevent, and it arrived by following the tool's own advice. `move-entry` re-keys the entry in place, preserving every field but `content_hash`.

### Features
- **`move-entry <old-path> <new-path>` — re-key a doc-index entry losslessly when a doc moves** (`scripts/doc-tools.sh`) — Staleness is computed from the `code_refs` / `code_commit` pair: the globs an entry watches, and the commit at which it was last verified against them. `remove-entry` deletes both, and `add-entry` cannot restore them — it re-reads `code_refs` from its stdin line (which the caller, post-removal, no longer has) and re-baselines `code_commit` to `HEAD`. Measured on a throwaway fixture rather than reasoned about: after `remove-entry` + `add-entry` on a moved doc, the entry carried `code_refs: []` and `code_commit: null`, and `check-freshness` reported `current` after **six** successive commits to the directory it had previously watched — permanently silent, because with no refs there is nothing to compare. The same move through `move-entry` reported `stale` / `code_changed` / `commits_behind: 1` after one. Even the more careful variant, where the caller happens to remember the refs and re-supplies them, still silently re-baselines `code_commit` to `HEAD` — an assertion that the doc was re-verified at a commit nobody read it at. `move-entry` takes exactly two arguments (the `old1 new1 old2 new2` varargs form would mis-pair silently on an odd count, so it is rejected rather than guessed at), preserves `code_refs`, `code_commit`, `last_verified`, `doc_type`, `status`, `replaces`, `superseded_by`, `implementation` **and any field the implementation does not know about** (verified with a synthetic sentinel key — the index schema is allowed to grow without this verb becoming a data-loss path), recomputes only `content_hash` from the file at the new path, and repoints any *other* entry's `replaces` / `superseded_by` that named the old path, rather than leaving it dangling at a key nothing can resolve. Failure modes are explicit and all exit non-zero: old key absent from the index is an error, not `remove-entry`'s tolerable batch `SKIP` (removal is idempotent; a re-key is not); new key already occupied refuses rather than overwriting, since clobbering a live entry is precisely the loss this verb exists to prevent; out-of-tree paths are rejected by the same `normalize_doc_path` boundary every path-taking verb has used since v2.13.1, so absolute in-tree paths work for both arguments. If the old file is still on disk the move proceeds with a WARNING rather than refusing — refusing would reject both a partially-staged `git mv` and a legitimate copy-then-reindex, while silence would let a copy-instead-of-move typo orphan an unindexed doc.
- **The five hook scripts and `update-index` now offer the non-lossy remedy** (`scripts/hooks/git/{pre-commit,post-merge,post-checkout}`, `scripts/hooks/claude/{pre-commit-gate,post-commit-sync}.sh`, `scripts/doc-tools.sh`) — This is where the defect actually reached users. Detection has always been there: every hook reports an indexed doc that no longer exists on disk. But the advice attached to it named only `remove-entry` and `deprecate-entry` — a deletion remedy offered for what is more often a rename. The advice now leads with `move-entry <old> <new>` for the rename case and says why (`remove-entry + add-entry would drop its code_refs, leaving an entry that can never go stale`), keeping the deletion verbs for actual deletions. The two installed copies under `.claude/hooks/` are mirrored so the self-installed tier stays in lockstep with its templates. `usage()` gains a `move-entry` entry, guarded by a test so it cannot silently drop back out.

### Fixes
- **`add-entry` and `build-index` minted `code_refs: [""]` from an empty refs field** (`scripts/doc-tools.sh`) — A mapping line with no refs (`docs/x.md::spec`, a documented and supported form for a doc that watches nothing yet) produced a one-element array holding an empty string instead of an empty array. Both now write `[]`. To be precise about the blast radius, since it sits next to the `move-entry` work and is easy to overstate: this is an index-hygiene fix, not a staleness fix. `[""]` and `[]` behave identically under `check-freshness` — both report `current`, because a null `code_commit` is what suppresses the comparison — so no verdict changes. What it fixes is a phantom ref propagating into every consumer that iterates `code_refs` (the CI coverage gate, the merge driver's per-entry union) as a ref that matches nothing and names nothing. Two new assertions pin both writers.

## v2.13.1 (2026-07-29)

Fixes a silent doc-index corruption: the subcommands that write or resolve index keys accepted paths that were not repo-root-relative and used them verbatim, producing entries no other command could ever find. Absolute in-tree paths are now normalized to the documented key form and paths outside the working tree are rejected with a non-zero exit. The documented relative-path form is unchanged — it is passed through byte-identically and never touches the filesystem. Also wires the five test suites into CI, which is why this class of defect was able to ship at all — and that CI, on its very first run, failed both legs on two pre-existing defects that had shipped in earlier releases: `build-index` could not write an index larger than ~420 entries on Linux, and every `doc-tools.sh` invocation aborted outright under macOS's `/bin/bash`. Both are fixed here.

### Fixes
- **`add-entry` and `build-index` wrote non-repo-relative paths verbatim as doc-index keys, silently creating entries no other subcommand could find** (`scripts/doc-tools.sh`) — The index is keyed by repo-root-relative paths and `docs/conventions.md` already documented it ("keyed by relative doc path"), but nothing enforced it. `cmd_add_entry` parsed its stdin line with `cut -d: -f1` and wrote field 1 straight into the `docs` map, so an absolute path became a key that `update-index`, `check-freshness`, `status`, `remove-entry`, `deprecate-entry`, the CI coverage gate and the merge driver all look up by exact string and can therefore never match. It printed `Added 1 entry` and exited 0 while doing so; in a downstream repo this corrupted 15 entries before a coverage gate caught them. `build-index` had the identical `cut`-and-write defect. `remove-entry` and `deprecate-entry` carried the same silent-acceptance shape from the other side — an absolute path reported "not found in index" and exited 0, a no-op for a caller asking to remove a real entry — while `update-index` and `status` already failed loudly but now resolve such a path instead. `deprecate-entry --superseded-by` is stored in the index as a doc reference, so it takes the same contract. Fix: a shared `normalize_doc_path` (with `_physical_path` and `_has_dot_segment`) rewrites an absolute in-tree path to its relative form, rejects anything outside the working tree or otherwise unresolvable with a stderr error and a non-zero exit before any write, and collapses `.` / `..` / `./` segments so `./docs/x.md` cannot become a second key for `docs/x.md` — while leaving dots inside filenames (`docs/v1.2/x.md`) alone. Resolution is physical rather than lexical because macOS `mktemp -d` returns `/var/…`, a symlink to `/private/var/…`, which a string-prefix comparison misjudges as out-of-tree; it also does not require the leaf to exist, since `add-entry` deliberately supports not-yet-written docs (null `content_hash`). Failure handling differs by semantics on purpose: `add-entry` is incremental, so the valid lines still apply and the command exits non-zero, whereas `build-index` REPLACES the index — where a partial write would silently drop docs — so a single bad line aborts before anything is written. `set-implementation` and `implementation-status` were checked and are correctly out of scope; they operate on files on disk, never on index keys. `add-entry`, `remove-entry` and `deprecate-entry` had **zero** test coverage, which is how this shipped: 15 new cases / 39 assertions cover both the fix and the relative-path control, and were confirmed red (25 failing) against the pre-fix script before it was re-applied.
- **`add-entry`'s summary ended in a colon promising a list it never printed** (`scripts/doc-tools.sh`) — `Added N entries:` was followed by nothing at all. It now enumerates the paths it added, matching its siblings `update-index` / `remove-entry` / `deprecate-entry`, drops the trailing colon when nothing was added, and reports the rejected count on the new failure path.
- **`build-index` could not write an index past ~420 entries: `jq: Argument list too long`, exit 126** (`scripts/doc-tools.sh`) — The accumulated `docs` object was handed to the final `jq -n` as `--argjson docs "$docs_json"`, i.e. as a single argv string. Linux caps ONE argument at `MAX_ARG_STRLEN` (32 pages = 131072 bytes) however large `ARG_MAX` is, so at ~312 bytes per entry the command died at roughly 420 docs — and a consuming project's ~3969-doc corpus was three million bytes past it. It failed hard and wrote nothing, so this is a hard ceiling on index size, not a corruption. macOS has no per-argument cap and only the ~1 MB total `ARG_MAX`, which is exactly why the defect reproduced on the ubuntu leg, passed on the macOS leg, and never once showed up in a local run — two independent local runs reported all-green while CI was correct. `check-freshness` carried the same shape in its final `jq -n` (`--argjson docs` plus `--argjson untracked_docs`) and would have hit it at a similar size. Fix: every unbounded value now reaches `jq` via `--slurpfile` from a tempfile instead of argv. `build-index`'s per-entry accumulation moved with it — it previously rebuilt the whole object each iteration (`docs_json=$(echo "$docs_json" | jq '. + {…}')`), which was also O(N²) in bytes re-serialized; entries are now appended as JSON-lines and merged once with `jq -cs 'reduce .[] as $row ({}; . + $row)'`, the same accumulator `check-freshness` has used since v2.12.1. Last-key-wins semantics on a duplicate path are preserved. The index is now rendered to a tempfile and `mv`'d into place, so a failed render can no longer truncate a good index — the previous code built the JSON in a variable first and got that property by accident. New regression test asserts both commands succeed on an index whose serialized `docs` object exceeds 1.2 MB; it is sized past macOS's total `ARG_MAX` as well as Linux's per-argument cap, so it guards both legs rather than only the one that happened to fail. Confirmed red against the pre-fix script on macOS (`Argument list too long`, exit 126, no index written).
- **Every `doc-tools.sh` invocation aborted under macOS's `/bin/bash`: `local: -A: invalid option`, exit 2** (`scripts/doc-tools.sh`) — `cmd_fragments_merge` declared `local -A is_canonical` and `local -A section_bodies`. Associative arrays are bash 4.0+; macOS ships bash **3.2.57** as `/bin/bash` (frozen at the last GPLv2 release) and has no associative arrays at all, so the declaration is a fatal parse-time error that takes down the whole script — not just the `fragments merge` path. It shipped in the fragment-consumer work and went unnoticed because nothing ran the suites under 3.2. Fix: the section map is two parallel indexed arrays with a linear lookup (section counts are single-digit; the scan is noise next to the per-fragment `git log` calls), and canonical-membership is a small loop rather than a set. - **New `doc-tools.sh fragments` subcommand**: Three verbs — `fragments list` (JSON enumeration with hash validity; skips non-numeric `PR-*.md` filenames with a warning), `fragments validate <path>` (exit 0 valid / 1 drifted / 2 missing), `fragments merge <start> <end> [--paths-out=<file>]` (markdown sections ready to insert under a `## vX.Y.Z` header; `--paths-out` records exactly which fragments were consumed so the release step can `git rm` only those, never destroying fragments belonging to still-open PRs). Encapsulates fragment-parsing in deterministic shell so the AI drafting step doesn't re-implement hashing or parsing in the prompt.
- **Three colocated shell helpers for the producer workflow**: `extract-context.sh` emits a JSON context blob (PR body, existing fragment, full and new commit ranges); `update-pr-body.sh` idempotently merges a managed section into the PR body with marker-injection, CRLF, and trailing-newline hardening; `commit-and-push.sh` stages, commits with a `[doc-superpowers]` prefix, and pushes the fragment back to the PR branch. The installer copies them to `.github/scripts/doc-pr-release/` alongside the workflow.
- **Fragment-format spec installed in consuming repos**: `hooks install --ci` now also drops a `RELEASE-NOTES.next/README.md` into the consuming repo (only if missing — never overwritten) that documents the fragment lifecycle, marker conventions, and the SHA-256 manual-edit protocol. Both halves of the lifecycle adhere to this format.
- **Unified Anthropic auth across all 6 AI workflows**: Every AI workflow (`doc-pr-release`, `doc-release`, `doc-review-pr`, `doc-audit-update`, `doc-spec-verify`, `doc-pr-full-cycle`) now resolves auth through a uniform preflight step: prefers `CLAUDE_CODE_OAUTH_TOKEN`, falls back to `ANTHROPIC_API_KEY`, fails fast with a clear error when both are unset, and emits a `::notice::` when both are set so the precedence is visible. The installer's secret-reminder lists both options with precedence documented.
- **Defense-in-depth recursion + verification guards on `doc-pr-release`**: `concurrency.cancel-in-progress` is now `false` so cancellation between `git commit` and `git push` can't leave orphan commits. A sentinel-commit check at the top of the workflow short-circuits when the head commit is the bot's own `[doc-superpowers] sync PR-<N>` — defending against `paths-ignore` gaps. A post-Claude verification step fails the workflow if the agent silent-skips (no sync commit AND no fragment on disk). An inline comment near the checkout step documents why `GITHUB_TOKEN` (not a PAT) is correct here.

### Fixes
- **Marker-count bug in `update-pr-body.sh` (`grep -oF` → `grep -cFx`)**: The validation count is now line-anchored so it agrees with the awk replace path (`$0 == start`). Previously, a mid-line marker in user prose would pass the count check, awk would no-op the replace, and a fresh managed section would be appended — leaving the stray marker stranded. Added a belt-and-suspenders any-occurrence vs line-occurrence comparison that fails closed on any mismatch.
- **Non-fast-forward push handling in `commit-and-push.sh`**: Push rejection now triggers `git fetch origin <branch>` and `git rebase origin/<branch>` (configurable retries, default 2). The agent prompt teaches the same human-edit-detected branch for corrupt fragments: post a PR comment, do not auto-overwrite.
