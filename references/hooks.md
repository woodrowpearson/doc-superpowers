# `hooks` — Install Workflow Hooks

**Read by** SKILL.md's `hooks` action — **REQUIRED** before running the installer. `$ROOT` is the
plugin root SKILL.md's *Detect Bundled Tooling* resolved (`$ROOT/scripts/hooks/install.sh` is the
installer, `$DOC_TOOLS` = `$ROOT/scripts/doc-tools.sh`).

Scaffolding command — installs opt-in hooks into the target project for automated freshness monitoring. No discovery phase needed.

**Setting a repository up?** `doc-superpowers setup` (`/doc-superpowers setup`; `references/setup.md`) chooses the tiers and the opt-in sets in one pass, from fixed safe defaults (the merge driver, the 5 report-only git hooks, the 3 Claude hooks; no CI, no download), shows every write first, and records the team's choice for `setup --apply` in each contributor's clone. It runs this installer for every tier and set it installs, so everything below still holds; this reference is the installer itself.

```
/doc-superpowers hooks install [--git [--merge-driver-only]] [--claude] [--ci] [--all] [--ledger] [--ledger-claude] [--search]
/doc-superpowers hooks status [--git [--merge-driver-only]] [--claude] [--ci] [--all] [--ledger] [--ledger-claude] [--search] [--json]
/doc-superpowers hooks uninstall [--git [--merge-driver-only]] [--claude] [--ci] [--all] [--ledger] [--ledger-claude] [--search]
```

(`install.sh print-merge-driver` prints the driver command; see *Merge driver only* below.)

Routes to `"$ROOT/scripts/hooks/install.sh" <subcommand> [flags]` (`install.sh help` lists every hook and workflow). `--ledger` and `--ledger-claude` are the work ledger's opt-in sets, and `--search` doc-search's, none of them part of `--all` (*Ledger sets* and *doc-search set* below). A flag the subcommand does not take exits 2; CI options (`--workflows`, `--base-branch`, `--cron`, `--ci-strict`, `--helpers`, `--force`, `--transient`) need `--ci` or `--all`.

**IMPORTANT:** ALWAYS use the installer script. NEVER manually add hook entries to `.claude/settings.json` or `.claude/settings.local.json` (the one exception: the work ledger's two hook modes, registered by a host in its own committed `.claude/settings.json` — see *Registering the ledger hooks in your own settings.json* below), and never copy hook templates by hand — the installer renders the templates (the `__DOC_TOOLS_RESOLVE__` placeholder becomes the program that finds `doc-tools.sh`), merges settings per entry, and refuses unsafe targets. Hand-made entries break.

**Where it writes.** Every subcommand acts on the repository holding the current directory, at its top level (`git rev-parse --show-toplevel`; a linked worktree or a submodule is its own top level), so it can run from a subdirectory. Git hooks go where git runs them (`git rev-parse --git-path hooks`: a repository-local `core.hooksPath`, a worktree's common dir, a submodule's `.git/modules/<name>/hooks`). It refuses — writing nothing — when:
- `core.hooksPath` comes from the user's global or system git config (every repository's hooks dir; a repository-local one, or a worktree's with `extensions.worktreeConfig`, is this repository's): tell the user to set a repository-local one or unset it. `uninstall --git` refuses it too, and leaves hooks an older installer put there for the user to delete by hand;
- a write target, or a directory on the way to it, is a symbolic link (a committed link could point at `~/.bashrc` or `~/.claude`): tell the user which path, never work around it;
- `.claude/settings.local.json` is not one JSON object, or `.claude/doc-superpowers/installed.json` cannot be read (see *State*).

**What it owns.** Only what it can name exactly: a hook whose first lines carry `doc-superpowers hook v<N>`; the `# doc-superpowers:begin` … `:end` block in a hook of the user's, in `.gitattributes` and in git's `info/exclude`; the `merge.doc-index.*` git config; each settings hook *entry* whose command runs `.claude/hooks/doc-superpowers/{pre-commit-gate,post-commit-sync,session-summary}.sh`, and those scripts' shared `hook-lib.sh` beside them (other entries and groups — even ones mentioning doc-superpowers — are the user's and survive install and uninstall byte-for-byte); a workflow whose first lines carry `doc-superpowers workflow v<N>`; for the work ledger's two sets (*Ledger sets* below), the `# ledger-superpowers:begin` … `:end` block in a git hook and in git's `info/exclude` (a hook the set created holds only `#!/bin/sh` and that block), and each settings entry whose command runs `.claude/hooks/doc-superpowers/{ledger-session-notices,ledger-state-watch}.sh`, with those scripts. The two marker pairs never match each other, so each uninstall takes only its own block. Uninstall is the inverse of install: an integrated hook of the user's comes back byte-for-byte, a `.gitattributes` or settings file the installer created is removed, and only the state file stays.

**Tier options:**
- `--git` — Git hooks: pre-commit (freshness gate on the staged tree, so it reports the commit being made: the docs its staged paths reach and every entry the staged index adds; an indexed doc the commit leaves out is "not in this commit" — `git add` it — when it is on disk, "missing from disk" with `move-entry` advice when it is gone; with `docs/spec-claims/` present, a claims leg runs first, with or without a doc-index: `doc-tools.sh claims validate --staged`, whose findings block the commit whatever `DOC_SUPERPOWERS_STRICT` says, while its advisories only print and a check that cannot run — exit 2 or 3, or a doc-tools older than the `claims` verb — prints one line and blocks only under STRICT; `DOC_SUPERPOWERS_CLAIMS_SKIP=1` bypasses that leg alone), post-merge (stale alert), post-checkout (branch check), prepare-commit-msg ("already stale" comments, editor commits only), pre-push (release reminder for the pushed refs; with `docs/spec-claims/` present, an advisory claims leg for every pushed branch, tagged or not: `claims run --planes-of` over the commits the push adds — `<remote oid>..<local oid>`, or from the merge-base with the config's `base`, else `origin/main`, for a new branch and whenever the remote oid is not an ancestor of the local one (a force-push, or a remote commit not fetched) — and, once per push, for the first pushed ref whose oid is HEAD's commit (attest judges HEAD), `claims attest --plan` for each plan with gate records but no `final.json`; for each branch it runs for it prints `claims (advisory): <n> red, <m> indeterminate`, zero counts included, and the finding lines, never changes the exit code, and `DOC_SUPERPOWERS_CLAIMS_SKIP=1` turns it off). Without `docs/spec-claims/` neither claims leg runs, and the hooks behave as before. `DOC_SUPERPOWERS_QUIET=1` silences the pre-commit claims leg's output, never its exit code: a finding still blocks the commit, with nothing printed. Pre-push exits at once under QUIET, so its claims leg does not run at all. Also registers the `docs/.doc-index.json` custom merge driver (`scripts/merge-doc-index.sh`) via `git config` + a marked `.gitattributes` block; re-running `install --git` re-registers a pre-3.0 (pinned) registration. When the user already has a hook, it is kept: if it is a shell script (`sh`, `bash`, `dash`, `zsh`, … or no `#!` line), a marked POSIX block goes right after its `#!` line and runs our copy (`.doc-superpowers-<hook>` beside it) with git's arguments — pre-commit passes our exit code on, so `DOC_SUPERPOWERS_STRICT=1` blocks; pre-push hands both hooks the same ref lines on stdin. A hook in another language is skipped with a message. Re-install refreshes the copy and replaces an older block.
- `--claude` — Claude Code hooks, **per-user**: registered in `.claude/settings.local.json` with commands `bash "$CLAUDE_PROJECT_DIR"/.claude/hooks/doc-superpowers/<hook>.sh`, and both that file and `.claude/hooks/doc-superpowers/` are excluded from git through git's `info/exclude` (they hold this machine's paths; each contributor installs their own). If the repository tracks either, the installer prints the command that untracks both (`git rm -r --cached --ignore-unmatch -- .claude/settings.local.json .claude/hooks/doc-superpowers`) and warns that pulling that commit deletes them from every other clone: relay that each teammate re-runs `install --claude` after pulling (a lost permission allowlist comes back with `git show ORIG_HEAD:.claude/settings.local.json`). PreToolUse pre-commit gate, PostToolUse post-commit sync, Stop session summary. They read the event JSON on stdin and answer with `additionalContext` (for Claude) and `systemMessage` (for the user). Under `DOC_SUPERPOWERS_STRICT=1` the gate exits 2 with the reason on stderr, even under `DOC_SUPERPOWERS_QUIET=1`, because that is Claude's feedback. It gates `git … commit` only in command position, so `echo git commit` is not a commit. It defers `git add … && git commit` and `commit -a` to the git pre-commit hook, which sees the real index — and counts that hook only when it is the doc-superpowers one or holds the current integration block. Stop fires after every response, so the summary covers only working-tree changes. The three scripts source one shared library, `hook-lib.sh`, installed beside them (never registered). It keeps every string a hook emits (`systemMessage`, `additionalContext`, the stderr of a STRICT block) under Claude Code's 10,000-character hook-output limit, past which Claude gets only a 2,000-character preview: a list names its first entries (10 in a one-line summary, 15 lines in a report section, 3 changed refs per doc, each list also held to 2,500 characters), then `…and N more (run 'doc-tools.sh check-freshness' for the full list)`, and each string is cut at 9,000 characters as a backstop. Each check runs under a watchdog, inside the 10 s timeout the installer registers: 7 s for the gate and the sync hook, 2 s for the summary. Past it the check is killed with everything it started, and the hook says `check skipped (budget)`; under STRICT the gate blocks instead, because a hook Claude Code times out gates nothing.
- No hook runs `update-index` or writes the index: re-baselining a doc stays a reviewer's step. In the `--git` and `--claude` tiers, a hook whose check fails (jq missing from PATH, a corrupt index) prints one line and blocks only under STRICT, and absent tooling is silent; the ledger sets differ (*Ledger sets* below: their pre-commit leg blocks on any non-zero exit, their pre-push leg refuses, and their post-commit leg pushes to the remote). Installed hooks find `doc-tools.sh` by the merge driver's rule: for a plugin-cache install, the newest version-named sibling in numeric order (a plugin update needs no re-install; other sibling directories never run); for a checkout, its own pinned path.
- `--ci` — CI/CD workflows. **Default: the two shell workflows** (`doc-freshness-pr`, `doc-freshness-schedule`); the other templates — the Claude-powered ones and the shell workflow `doc-ledger-publish` — are opt-in by name (`--workflows=…`); `--workflows=all` installs every template except those removed on purpose, and except `doc-ledger-publish` on a host without `docs/ledger/config.json` (its every-30-minutes cron would bill no-op runs: one note line says it was skipped; naming it installs it). `install.sh help` lists `doc-ledger-publish` in its own group, "shell, opt-in by name", apart from the Claude-powered ones. Plus `doc-tools.sh` vendored into `.github/scripts/` through `doc-tools.sh tools install`, with the helper directories exactly while an installed workflow runs them (every workflow runs step scripts from `.github/scripts/doc-superpowers-steps/`; the work ledger's helper set, `.github/scripts/ledger/` and `.github/scripts/adapters/`, ships only on a ledger host — `docs/ledger/config.json` exists — with `doc-ledger-publish` and with every workflow that runs the claims check (`doc-freshness-schedule`, `doc-spec-verify`), because the claims check V5 reads ledger trackers with it; without the config nothing of it is vendored, a set vendored before is removed (byte-identical files only), and nothing is said. On a ledger host `status --ci` flags a claims workflow without it, and `ledger init --accept` says the same when it writes the config: re-run `install --ci` and commit what it writes. A file of the host's own there with a shipped file's name is replaced). `doc-index-update` was **retired in v3.0.0** (it re-baselined every doc edited on the base branch, unread, and failed every run): any `install --ci` removes an installed copy the installer owns (its `doc-superpowers workflow v<N>` marker) and drops its state entry; a file of that name without the marker is kept and reported (`Kept …`) — relay it, never delete it for the user.

**Ledger sets** (the work ledger, opt-in; never part of `--all`; each refuses to install, exit 1, writing nothing, without `docs/ledger/config.json`; like the git and Claude tiers per-clone / per-user and never recorded in `installed.json`):
- `--ledger` — the git legs, as marked blocks (never whole files) where git runs hooks. In the git tier's own hook the block goes after its header comments, and `install --git` puts it back whenever it writes its hook whole, so the order of the two installs never changes the result; `uninstall --git` leaves a hook holding the block as `#!/bin/sh` and the block. In a hook of yours (a shell script) the block goes after the `#!` line, a git-tier block right there, and the leading comment lines — before your code, so a trailing `exit 0` of yours cannot skip it; your hook's mode is kept and uninstall restores it byte for byte. A hook in another language is skipped with a message. With no hook, the set creates a `#!/bin/sh` one. Each leg is silent without the config. Under `DOC_SUPERPOWERS_LEDGER_SKIP=1` (the ledger legs) or `DOC_SUPERPOWERS_SKIP=1` (every doc-superpowers hook) each leg is skipped: pre-commit and pre-push print a line naming the variable, and post-commit is skipped silently. Unlike the git tier's hooks, a failing ledger check is not STRICT-only:
  - pre-commit: `doc-tools.sh ledger validate --staged`; any non-zero exit — 1 (findings) or 2 (it could not run) — blocks the commit. A `doc-tools.sh` that cannot be found prints one line and does not block. In a shallow clone with config `trailers.since: "adoption"` whose boundary hides the adoption commit, the check exits 2 and so blocks: deepen the clone (`git fetch --unshallow`) or name the commit (`references/ledger.md` → *Shallow clones*).
  - pre-push: for each ref pushed (deletions aside), `ledger validate --pushed <remote oid>..<local oid>` — from all zeros for a new branch and when the remote oid is not here or not an ancestor, — checks the provisional keys the branch adds since its merge-base with config `base`, for a new branch and an existing one alike (every one at a new branch's tip, or every one the range adds, when the base does not resolve), so a provisional key that came from the base — a new branch forked after it landed, or an existing branch that merged the base since — never blocks it; it refuses a push whose branch adds a provisional key in `keys.mode` `cas` (merge mode lets it through); a refused key the base carries too is named with `ledger finalize --all`. git's ref lines are copied to a temp file that becomes the hook's stdin again, unread, so whatever runs after the block — the git tier's leg, your own checks, a token guard — reads exactly the lines git sent; the file is unlinked before any check runs. No temp file, or a copy or redirect that fails (a full disk): the push is refused with a reason line, because git's lines are already gone from stdin and the code after the block would read nothing and pass. The git tier's own pre-push block (`--git`) applies the same rule.
  - post-commit: `ledger inflight --push` in the background — the commit never waits, and the job holds none of its output (stdin `/dev/null`; stdout and stderr to `<git common dir>/doc-superpowers/ledger/push.log`). It pushes only with `inflight.enabled` and commits beyond the base, and ignores a hangup; `doc-tools.sh` reaps its push and transport on TERM / INT. The job still holds the terminal (macOS has no `setsid`), so it is set up not to ask anything:
    - `GIT_TERMINAL_PROMPT=0` stops git's own prompts.
    - `GCM_INTERACTIVE=never` stops Git Credential Manager's.
    - ssh runs with `-o BatchMode=yes`, following git's own precedence (`GIT_SSH_COMMAND` > `core.sshCommand` > `GIT_SSH` > `ssh`): appended to `GIT_SSH_COMMAND`, else to `core.sshCommand` (exported as `GIT_SSH_COMMAND`), else to `ssh`. A key that needs a passphrase, or an unknown host key, then fails the push and `push.log` says so.
    - `GIT_SSH` is never changed. Only when neither `GIT_SSH_COMMAND` nor `core.sshCommand` is set does git run it, and then the block adds nothing, so that program of yours could still prompt.
- `--ledger-claude` — the two Claude Code events alone, registered in `.claude/settings.local.json` and excluded from git through their own `info/exclude` block. It never installs the general `--claude` tier (whose gate a host may not want); `hook-lib.sh`, which the `--claude` tier's three scripts and `ledger-session-notices.sh` source (`ledger-state-watch.sh` does not), comes with either and goes with the last script that sources it: `uninstall --claude` keeps it while a ledger script is installed. Both scripts are thin wrappers over a hook mode of a ledger verb (`ledger notices --hook`, `ledger state-watch --hook`: the same output), exit 0, print one JSON object or nothing, and are off under `DOC_SUPERPOWERS_LEDGER_SKIP=1` or `DOC_SUPERPOWERS_SKIP=1`:
  - `ledger-session-notices.sh` (SessionStart): `doc-tools.sh ledger notices --hook` — the unacked `stop` and `heads-up` notices for the session's branch, run offline (as `DOC_TOOLS_LEDGER_OFFLINE=1`: no fetch, even on an expired cache), as `systemMessage` and `additionalContext`: a count line and the notices, at most 15 lines with the rest counted. The wrapper gives the run 2 s (hook-lib.sh `_bounded`); past that it is killed and a one-line "(budget)" note says so. `info` notices are left to `ledger notices`. With no notices, or with `inflight.enabled` off (where the wrapper does not run `doc-tools.sh` at all), the hook is silent; a check that fails is one "cannot list the in-flight notices" line.
  - `ledger-state-watch.sh` (PostToolUse, matcher `Write|Edit|MultiEdit`): `doc-tools.sh ledger state-watch --hook` (with no `state_watch.paths` the wrapper does not run it) — when a write lands under a `state_watch.paths` entry and what was written (Write's content, Edit's `new_string`, MultiEdit's edits) names an item key (of a registered ledger or `legacy_ids`) and one of `state_watch.patterns` (text, any case), one advisory line (`additionalContext`) suggests `doc-tools.sh ledger note <key> "…"`. A `state_watch.paths` entry is a path: a leading `~/` is `$HOME` (with `HOME` empty or unset, such an entry names nothing), an absolute one is itself, any other is under the project; `*` matches within one path segment and every other character — spaces, a `~` anywhere else, `?`, `[` — is itself; it matches the file and anything below it. Nothing is word-split or globbed against the disk; either path may cross a symbolic link: the directories that exist are compared resolved, so a project reached through a symlinked path still matches. Never blocks. With `state_watch.paths` set and no `state_watch.patterns` it never fires: `status` warns `⚠ ledger-state-watch never fires` where the hook is installed, and `ledger validate --all` reports it (class `config`, advisory).
- **Registering the ledger hooks in your own settings.json.** `--ledger-claude` writes the per-user `.claude/settings.local.json`, which does not travel across worktrees. A host that registers hooks in its committed `.claude/settings.json` can point them at the hook modes instead — stable entry points beside `doc-tools.sh`, no installed script needed:

  ```json
  {
    "hooks": {
      "SessionStart": [
        { "matcher": "", "hooks": [ { "type": "command", "timeout": 10,
          "command": "bash \"$CLAUDE_PROJECT_DIR\"/<path>/doc-tools.sh ledger notices --hook" } ] }
      ],
      "PostToolUse": [
        { "matcher": "Write|Edit|MultiEdit", "hooks": [ { "type": "command", "timeout": 10,
          "command": "bash \"$CLAUDE_PROJECT_DIR\"/<path>/doc-tools.sh ledger state-watch --hook" } ] }
      ]
    }
  }
  ```

  `<path>` is a `doc-tools.sh` that every worktree resolves, with its `ledger/` directory beside it (a committed copy of the skill's `scripts/`, or an absolute path in place of `"$CLAUDE_PROJECT_DIR"/<path>`). Each mode reads the event on stdin (an event that is not one JSON object: silent), cds to the top level, prints one hook object or nothing, never fetches, takes no other option and always exits 0 — a usage error, no repository, no `docs/ledger/config.json`, `DOC_SUPERPOWERS_LEDGER_SKIP=1` and `DOC_SUPERPOWERS_SKIP=1` all print nothing. `notices --hook` prints the same object as `ledger-session-notices.sh`, with nothing printed when `inflight.enabled` is off; `state-watch --hook` the same as `ledger-state-watch.sh`. What a direct registration lacks is the wrapper's 2-second watchdog: the entry's `timeout` bounds it instead. Do not register both a mode and `--ledger-claude` for the same event: each would print its notices. `status` never inspects entries you register yourself, so an upgrade is yours to make: a state-watch entry registered for `Write|Edit` (before 3.4.0) misses MultiEdit's writes until you change its matcher to `Write|Edit|MultiEdit`.
- `uninstall --ledger` and `uninstall --ledger-claude` each remove their own set (`--all` removes neither); `status` reports each set in its own section (plain `status` shows them after the tiers; `status --ledger` / `--ledger-claude` show one; `status --claude` also shows the `--ledger-claude` section once any of that set is installed, as both live in one settings file; `status --all` shows the three tiers only).

**doc-search set** (`--search`: doc-search's MCP server, opt-in; never part of `--all`; like the ledger sets, never recorded in `installed.json`; `references/search.md` is the server's reference). It refuses to install, exit 1, writing nothing, without `docs/search/config.json` (`doc-search init` writes it), and `install` / `uninstall` need `jq` (without it they stop, writing nothing). Two things, both meant to be **committed**, so every contributor with `uv` gets the server:
- `.claude/doc-superpowers/search-mcp.sh` — the launcher, a byte copy of the plugin's `scripts/search/launch.sh`. It holds no machine path: it finds doc-superpowers when it runs (`$DOC_SUPERPOWERS_ROOT`, this checkout when it is doc-superpowers, else the newest version in the plugin cache).
- the `doc-search` key of the project's `.mcp.json` `mcpServers`: `{"command": "sh", "args": [".claude/doc-superpowers/search-mcp.sh", "serve"]}`, merged per key — every other server and key of the file is kept, and a file already holding exactly that entry is not rewritten. A `.mcp.json` that is not one JSON object, or whose `mcpServers` is not an object, is refused (fix it by hand), never rewritten; a symbolic link at either path is refused like any write target.

`uninstall --search` removes that key and the launcher, and `.mcp.json` itself when that leaves it exactly `{"mcpServers": {}}`. `status` (plain, or `--search`) reports the set in its own section: the launcher `installed` (the plugin's copy, byte for byte), `outdated` (`re-run install --search`) or not installed, and the entry registered, registered with a different command, or not registered. Without `docs/search/config.json` and nothing installed, the section is one plain `not enabled` line; an installed launcher or entry there reads `⚠ docs/search/config.json is missing` (the server answers "not enabled"). `status --json --search` reports it as `.tiers.search`, e.g. `{"launcher": "installed", "mcp_entry": "registered"}` (*Machine-readable status*).

**Status and upgrades.** (`status --json` gives the same verdicts machine-readably: *Machine-readable status* below.) `status` compares each installed git hook, the local copy an integrated hook runs, each Claude script and each settings command with what this install would write (the install date on line 2 aside). A hook of another doc-superpowers version carries the same marker, so anything else reads `⚠ … outdated: re-run install --git` (or `--claude`): re-run that tier. The ledger sets say the same in their own sections — `re-run install --ledger` for an outdated block, `re-run install --ledger-claude` for an outdated script, command or matcher. A 3.3.0 `--ledger-claude` install registered state-watch for `Write|Edit`: it reads `outdated (registered for other tools than matcher "Write|Edit|MultiEdit")` until `install --ledger-claude` is re-run, which replaces the entry in place. An integrated pre-push block from before 3.3.0 (which let a push through when it could not copy git's ref lines) reads outdated until `install --git` is re-run; so do the 3.2.0 Claude tier's scripts (their shared `hook-lib.sh` changed) until `install --claude` is. In a repository without `docs/ledger/config.json` where nothing of a ledger set is installed, that set's section is one plain `not enabled` line, no warning; an installed leg there reads `⚠ docs/ledger/config.json is missing`. After upgrading from 2.x, walk the user through `$ROOT/README.md` → *Upgrading from 2.x* (v2's AI workflows, the per-user Claude tier, hooks in unconfigured directories, retyping design specs).

**Merge driver only** (`--merge-driver-only`, with `--git` or `--all`; without the git tier it exits 2). For a host that runs its own git hooks and wants only the `docs/.doc-index.json` merge driver: `install --git --merge-driver-only` registers the `merge.doc-index.*` git config and writes the marked `.gitattributes` block, and nothing else — no hook, no local copy, and hooks already there (yours, or the git tier's) are left as they are. It writes no hook, so a global `core.hooksPath` does not refuse it. Run from a plugin copy without `scripts/merge-doc-index.sh` beside it, it has nothing to register: it exits 1, naming the missing script, and writes nothing. `uninstall --git --merge-driver-only` removes only those two (the hooks stay); `status --git --merge-driver-only` reports only the driver and `.gitattributes` lines. Nothing about the git tier is recorded in `installed.json` (per clone), so a driver-only install is not either. A host that registers the driver itself gets the exact value from `install.sh print-merge-driver` (one line; no repository needed): `git config merge.doc-index.name "doc-superpowers index merger"` and `git config merge.doc-index.driver "$(install.sh print-merge-driver)"`, plus a `docs/.doc-index.json merge=doc-index` attribute. The value resolves the driver when a merge runs (the newest plugin-cache version, or the checkout's pinned script), so it survives plugin updates; `status` reads a registration equal to it as `registered`.

**Machine-readable status** (`status --json`). One JSON object on stdout and exit 0 (a usage error still exits 2): the states are the verdict, so a host's self-heal check reads them instead of grepping the human lines, which stay as they were (`status` without `--json` prints them unchanged). It covers the git, Claude and CI tiers — all three, or those named (`--git`, `--claude`, `--ci`, `--all`; `--merge-driver-only` narrows the git tier); the ledger sets have no JSON status, and `--json` with `--ledger` or `--ledger-claude` exits 2. doc-search's set is reported as `.tiers.search` **only when `--search` is named** (alone, when it is the only one named; never with the default or `--all`, so the existing shape stays as it was). A tier not asked for is absent from `.tiers`. Shape (schema `doc-superpowers-hooks-status/1`; a later version adds keys, and a changed meaning gets a new schema string):

```json
{
  "schema": "doc-superpowers-hooks-status/1",
  "repo": "/abs/top/level",
  "plugin": "/abs/plugin/root",
  "tiers": {
    "git": {
      "hooks_dir": ".git/hooks",
      "hooks_path_scope": null,
      "hooks_path_foreign": false,
      "merge_driver_only": false,
      "hooks": { "pre-commit": { "state": "installed", "installed": "2026-10-18" }, "...": {} },
```

**Hook budgets and advice** (the git and Claude tiers; one optional, committed file, `.claude/doc-superpowers/hooks.conf`, `key = value` lines, `#` comments, the last line for a key wins — read with `awk`, never sourced; an environment variable overrides its key):

| Knob | Env | `hooks.conf` key | Default | Effect |
|---|---|---|---|---|
| Git-hook check budget | `DOC_SUPERPOWERS_HOOK_BUDGET` | `hook_budget` | `20` (seconds) | The freshness check of pre-commit, prepare-commit-msg, post-merge and post-checkout runs under a watchdog (the Claude tier's: its own process group, killed with everything it started). Past the budget the hook prints one line — `doc-superpowers: <hook>: check skipped (budget): … run 'doc-tools.sh check-freshness' by hand …` (prepare-commit-msg: a comment line) — and lets git go on; under `DOC_SUPERPOWERS_STRICT=1` the pre-commit blocks instead, as for a check that cannot run. `0` is no budget; a value that is not digits reads as the default, and one past a day (more than `86400`, or more than six digits once leading zeros are dropped) reads as `0`, no budget, since `sleep` may not take it (macOS's rejects 4294967295 s and up) and a watchdog whose sleep fails must not fire at once (one whose sleep fails for any reason never fires). A hook interrupted mid-check (`INT`, `TERM`, `HUP`: a ^C at the terminal does not reach the check's own process group) kills the check's group and the watchdog, then dies of that signal (exit 128+n). The Claude tier keeps its fixed budgets (7 s, 2 s), inside the timeout the installer registers |
| Advice | `DOC_SUPERPOWERS_ADVICE` | `advice` | `/doc-superpowers <action>` | The command the git and Claude hooks advise (`update`, `audit`, `release`, and the gate's `hooks install --git`): `off` drops it (a line that is only advice goes, a line that also says something else keeps the rest, e.g. `DOC_SUPERPOWERS_SKIP=1 bypasses.`); any other text is a template whose every `{action}` becomes the action (`make docs-{action}` → `make docs-update`; a template without `{action}` is used as is); `on` (or unset) is the default |

The git hooks are also scoped where scoping is exact: pre-commit (and the Claude gate) judge the entries a staged index adds against their own code refs rather than the whole index (unscoped only when an added entry has no code ref, which no filter keeps); post-merge and post-checkout were already scoped to the files the merge or switch changed, which on a large merge can still reach most of the index — the budget is their backstop. Each git hook carries the watchdog and the settings readers itself (a region kept byte-identical with `hook-lib.sh`, pinned by `test-hooks.sh`), so the git tier works without the Claude tier. Changing these hooks makes earlier installs read `outdated`: re-run `install --git` (and `install --claude`, whose `hook-lib.sh` changed).

| `doc-audit-update` (AI) | push to a non-base branch that leaves indexed docs stale or missing (not Dependabot's) | contents: write | **a checked step commits `docs/` and indexed docs to that branch** — the doc updates and the audit report itself (`docs/plans/<date>-audit-report.md`), one per run that finds work |
| `doc-review-pr` (AI) | PR open/sync touching indexed docs or their code; `@claude` PR comments by members | contents: read, pull-requests + issues: write | PR comments only (its tools edit no file — see *What an AI job's agent can reach*) |
| `doc-release` (AI) | push to `release/**` | contents + pull-requests: write | a checked step commits the release files to a new branch and opens a PR |

How every workflow behaves (tell the user when they ask what they agree to):
- A check that cannot run is never "all current": the freshness PR check warns (fails under `--ci-strict`), the schedule run fails and never closes the issue, and the AI jobs' scope step fails the job. Results stay in files; only counts reach step outputs.
- Which docs and code a change touches comes from the doc index (`check-freshness --code-refs-from`), not from path filters in the workflow.
- Spec claims (`doc-spec-verify`'s `claims` job, and a step of `doc-freshness-schedule`) run only with `docs/spec-claims/`; without it the step reports `status=disabled`, runs nothing, and the schedule's issue body is unchanged. On a PR, `claims-check.sh pr` runs `claims validate --all`, `claims run --all` and `claims attest --plan <p> --final` for each plan it selects, every call with `--base <the PR's base SHA>`. A plan is selected when it is a tracked file matching config `plans` (default `docs/superpowers/plans/*.md` and `docs/plans/*.md`), has a `docs/spec-claims/gates/<plan-stem>/` directory, is `Completed` or has a `final.json` there, and the PR changes the plan file or that `final.json`: a plan the PR does not touch is never attested. Findings fail the job, and a check that cannot run (an adapter reports `indeterminate`, as one does when the runner lacks the tests' environment — see *Test-environment setup* below) warns, and fails under `--ci-strict`. A PR that deletes a `docs/spec-claims/` its base has is itself a finding: a change cannot switch off the check that would judge it. The CI checkout holds no verdict store: promotions count by their stored digest, and V6 compares each changed promoted claim with its `promotion.proved`, so a field changed since the proof is still a finding (or `re-promote owed` under a covering `DOC-STALE`/`RETIRE`); a missing verdict with nothing changed is an `unverifiable-here` advisory. Weekly, `claims-check.sh scheduled` runs `claims run --all --scheduled --judge-sample 3`, `claims promote --reverify --all` and `claims validate --all` (`--base origin/<base branch>`): findings keep the audit issue open under `### Spec claims` with the week's judge sample, and the step fails only when nothing could run. The job's timeout is 30 minutes for those runs.
  - **Test-environment setup.** Both claims steps run the claims' adapters on a bare `ubuntu-latest` runner, so a host whose claim-bound tests need a toolchain or dependencies adds that setup before the claims step. Its durable home is an unmanaged copy of the workflow: delete the `doc-superpowers workflow v<N>` marker line from the installed file, and every later `install --ci` skips it (`Existing <name>.yml found (not doc-superpowers-managed), skipping.`) instead of re-rendering it. A step added to a managed workflow is lost at the next `install --ci`, which refreshes every managed workflow. From then on the copy is the user's to update. The step scripts it runs keep shipping only while some managed workflow is installed, and the ledger helper set only while a managed claims (or publish) workflow is, on a ledger host: unmanage every claims workflow there and the next `install --ci` removes the set, so the copy's claims V5 reports `ledger-unavailable` — keep one claims workflow managed (the set follows it).
  - `doc-freshness-schedule.yml` has no setup slot either, so without one its adapters report `indeterminate`. The issue closes only when the claims status is `ok` or `disabled`, and an `indeterminate` claims result never closes it (nor, on its own, opens one): an audit issue that is already open stays open for as long as the weekly runs stay `indeterminate`, even once the docs and the claims that did run are clean.
- **`doc-spec-verify`'s `claims` job runs the PR head's code**, with no agent involved: it checks out the head commit and runs that commit's `.github/scripts/` (`claims-check.sh` and the vendored `doc-tools.sh`), the claims' adapters and the tests they run. Whoever can push a branch to the repository decides that code (the job never runs for a fork's or Dependabot's PR). Its checkout sets `persist-credentials: false`, so `.git/config` holds no token, and the claims step is passed none in its `env:`; the amendment step after it runs the head's `.github/scripts/doc-pr-release/update-pr-body.sh` with `GH_TOKEN` (`contents: read`, `pull-requests: write`).
- AI workflows use the job's own `GITHUB_TOKEN` (`github_token: ${{ github.token }}`; no `id-token: write`), so `permissions:` bounds that token and its pushes start no other workflow run. They install this plugin from its GitHub tag `v<the installed version>`, run only for same-repository PRs (never forks or Dependabot), grant the agent a scoped `--allowedTools` list with `--max-turns`, and have `timeout-minutes`. The agent never commits: a later step (a pre-agent copy of the checker, git hooks and fsmonitor off — an integrity check against agent mistakes, not a sandbox: see *What an AI job's agent can reach*) refuses any changed path outside the workflow's set, then commits and pushes without force. The three that commit to a branch check out the branch and share one concurrency group per branch: never cancelled mid-run, pending runs queued in order (`queue: max`; on a GitHub Enterprise Server without it, delete that key). A `doc-audit-update` or `doc-pr-release` run whose branch received someone else's commits meanwhile ends green as superseded, committing nothing — that push starts a new run. `doc-pr-full-cycle` runs only when the PR is opened, so nothing would re-run it: its superseded run fails ("… received new commits during this run (…); nothing was committed to it. Re-run this workflow …"). A run whose branch moved only by doc-superpowers commits, or backwards, fails visibly — re-run it.
- **Commits and PRs made with the job's token start no workflow run** — of any workflow. The commit `doc-audit-update`, `doc-pr-full-cycle` or `doc-pr-release` pushes gets no check runs, and it is the branch head (`doc-pr-release` pushes after every author push), so a PR's required status checks wait at "Expected"; the PR `doc-release` opens gets none either. The author pushes another commit, or closes and reopens the PR, to run them.
- `doc-release` opens its PR with the job's token: the repository setting *Allow GitHub Actions to create and approve pull requests* must be on (the step says so when it is off). That setting also lets **any** workflow job with `pull-requests: write` approve pull requests — so require a human's review (below).

**What an AI job's agent can reach** (tell the user with the consent table). The scoped tools and the commit checker keep an agent on task; they do not contain one that is steered — and a PR, a commit message, a fragment or an `@claude` comment (tag mode hands every member's comment to the agent as its request) is text the agent reads, which can carry instructions:
- **Code.** A job whose tools edit no file (`doc-review-pr` and its `@claude` answer, `doc-spec-verify`) can still run code: the granted `git log` / `git diff` / `git show` take options such as `--output=<file>` (which writes any file, a git hook included) and run the programs git config can name. A job with `Edit`/`Write` and `doc-tools.sh` can too.
- **Secrets.** Code the agent runs sees the job's environment: the Anthropic credential and the job's token (`GH_TOKEN`) — `jq -n env` prints them (the `@claude` tag-mode job is not granted `jq`). `actions/checkout` also persists the job's token in `.git/config` (no AI job's checkout sets `persist-credentials: false`: the commit steps push with it; only `doc-spec-verify`'s `claims` job, which has no agent and runs the PR's own adapters, sets it), so the granted Read tool reads it in every AI job, the tag-mode `respond` job included. A granted `gh pr comment`, the action's tracking comment or a committed doc can publish them. No `permissions:` block bounds that.
- **The token, repository-wide.** `permissions:` bounds what the token may do, not where: with `contents: write` a steered writer can push to any unprotected branch or tag, or change `.github/scripts/doc-superpowers-steps/*.sh`, which later jobs run with the secrets (`resolve-auth.sh` receives both). With `pull-requests: write` it can comment, and — under the setting `doc-release` needs — approve pull requests.

Recommend, before any AI workflow: **protect the base branch and `release/**`** with required pull-request reviews from a human — approvals by GitHub Actions must not count — and no direct pushes, so nothing an agent pushes or approves reaches them unreviewed; and install only the AI workflows the user needs. Recommended hardening, not set by the templates: `CLAUDE_CODE_SUBPROCESS_ENV_SCRUB: "1"` in the `env:` of an action step makes Claude Code strip the Anthropic credential (and the other credentials it recognizes) from every command the agent runs — whether `gh` still authenticates under it is unconfirmed until a real run.

AI workflows need a `CLAUDE_CODE_OAUTH_TOKEN` (preferred) or `ANTHROPIC_API_KEY` repository secret. Do not combine `doc-review-pr` and `doc-pr-full-cycle` (both review every PR). Name only the workflows the user agreed to in `--workflows=`.

**CI-specific flags:**
- `--workflows=<csv|all|none>` — Workflow selection.
  - omitted: the recorded set (see *State*); a first install gets the two shell workflows.
  - CSV (e.g. `--workflows=doc-pr-release,doc-freshness-schedule`): install the listed workflows (names are basenames without `.yml`, repeats count once; an unknown name, a retired one — `doc-index-update` — or an empty list errors out). An explicit name overrides an earlier intentional uninstall.
  - `all`: every template, except those uninstalled on purpose.
  - `none`: no workflow, only the vendored `doc-tools.sh` (prefer `tools install` for that).
- `--base-branch NAME` — Target branch (default: `main`); a name git accepts, of letters, digits and `. _ / -` only (anything else could corrupt a workflow line).
- `--cron EXPR` — Schedule, 5 fields (default: `0 9 * * 1`).
- `--ci-strict[=true|false]` — Fail the PR checks on what is otherwise a warning (default false). It is rendered into two workflows: `doc-freshness-pr` then fails on stale docs and on a freshness check that cannot run, and `doc-spec-verify`'s `claims` job fails on a claims check that cannot run (an adapter `indeterminate` or failing; `claims-check.sh pr` under `DOC_SUPERPOWERS_STRICT=1`). Claims findings fail that job either way.
- `--helpers=<true|false>` — Deprecated, and inert: the helper directories ship exactly while an installed workflow runs them (the `doc-pr-release` producer helpers with `doc-pr-release`, the step scripts in `.github/scripts/doc-superpowers-steps/` with any workflow), whatever this flag says. Its only effect: `--helpers=false` is refused (non-zero, nothing written) while `doc-pr-release` is selected or already installed; a `doc-pr-release` uninstalled on purpose does not count. Do not pass it.
- `--force` — Also re-install workflows uninstalled on purpose. **Never pass `--force` unless the user asked for exactly that.**

**Uninstall-specific flags:**
- `--workflows=<csv|all|none>` — Which workflows (default: all, plus the vendored files and a retired `doc-index-update.yml` the installer owns). An unknown name exits non-zero; `doc-index-update` is accepted here (it removes an owned copy).
- `--transient` — Record the removal as temporary (`intentional:false`) so the next plain `install --ci` puts them back. Without it the removal is intentional.

Vendored files are removed through `doc-tools.sh tools uninstall`: a file with local edits (or from another plugin version) is kept and reported as `Kept …` — relay those lines to the user; the uninstall is not "clean" then. `RELEASE-NOTES.next/README.md` goes with the `doc-pr-release` helpers only when it is byte-identical to the plugin's fragment-format spec and the only file in `RELEASE-NOTES.next/`; an edited copy, and any fragment, stay.

**State** (`.claude/doc-superpowers/installed.json`, committed — tell the user to commit it with the workflows):
- The installer records the CI tier only (the git and Claude tiers are per-clone / per-user); a top-level `setup` object is `doc-superpowers setup`'s team record (`references/setup.md` → *The records*), which every write keeps: the workflow set (`installed`, or `uninstalled` with `intentional`), `base_branch`, `cron`, `ci_strict`, and each workflow's `installed_at` (set once, never rewritten on a refresh).
- A plain `install --ci` reproduces the recorded choices and refreshes exactly the recorded workflows (it adds no default); flags override a choice and are recorded. Upgrading a pre-3.0 install keeps the choices found in its rendered workflows.
- A doc-superpowers workflow on disk counts as installed whatever the state says, and is refreshed.
- An unreadable state file (a merge conflict, the wrong shape) is never overwritten: install and uninstall exit 1 and `status` warns. Have the user resolve the conflict, or move the file to `installed.json.corrupt` — the next install then rebuilds it from disk and installs nothing that is not already there.

**Standalone `tools` subcommand (v2.12.0+):**

For projects that want only `doc-tools.sh` (and optionally the CI helpers) without workflows, route to `$DOC_TOOLS tools …` directly instead of `hooks install --ci`:

```bash
$DOC_TOOLS tools install [--dest <path>] [--with-helpers | --helper <set>...]
$DOC_TOOLS tools uninstall [--dest <path>] [--helper <set>...]
$DOC_TOOLS tools status    [--dest <path>]
$DOC_TOOLS tools version
```

`--dest` defaults to `.github/scripts`. `--with-helpers` ALSO installs every helper set the CI templates run — `doc-pr-release/*.sh`, `doc-superpowers-steps/*.sh` and the `ledger` set — and `RELEASE-NOTES.next/README.md` if absent; `--helper <set>` (repeatable: `doc-pr-release`, `doc-superpowers-steps`, `ledger`) only those sets (the README comes with `doc-pr-release`). The `ledger` set is two directories: the work ledger's modules (`scripts/ledger/*.sh`, `*.awk`, `*.jq` → `<dest>/ledger/`) and the reference adapters (`scripts/adapters/*.sh` → `<dest>/adapters/`), which the vendored `doc-tools.sh` runs from beside itself — without them it exits 2 for an enabled ledger. `install --ci` uses exactly this, per installed workflow. Use it when the user wants to wire `doc-tools.sh` into their own (non-doc-superpowers) workflows. `tools uninstall` removes only files byte-identical to the plugin's copies (with `--helper`, only in those directories, keeping `doc-tools.sh`; with the `doc-pr-release` helpers, also an unmodified `RELEASE-NOTES.next/README.md` that is alone there): an edited or user-added file (and a copy from another plugin version) is kept and reported — tell the user, never delete it for them. `tools status` also says whether `RELEASE-NOTES.next/README.md` matches the plugin's spec: a pre-3.0 copy (it is created only when absent, so an upgrade keeps it) gives outdated advice — offer to replace it with the plugin's `scripts/hooks/ci/doc-pr-release/RELEASE-NOTES.next.README.md`. Both refuse a symbolic link at a destination or on the way to it. Run these from the plugin's `doc-tools.sh` (`$DOC_TOOLS`): a vendored copy cannot uninstall, cannot ship helpers, and `tools status` from it reports presence only (no drift, no version).

When no tier flags are provided via SKILL.md routing, present the options to the user (with the consent table for `--ci`) and pass the appropriate flags. The installer's interactive menu is for direct terminal invocation only.

## CI sub-workflows

The `--ci` tier's templates (a path holding a workflow that is not a
doc-superpowers one is skipped). The first two are the default set; the
others install only when named:

| Workflow | Trigger | Purpose |
|---|---|---|
| `doc-freshness-pr.yml` | PR open/sync | One PR comment listing the docs the diff leaves stale or missing (updated every push; STRICT fails the check) |
| `doc-freshness-schedule.yml` | Weekly cron | Keeps one audit issue open while docs are stale or missing, or spec claims have findings; closes it after a clean check |
| `doc-audit-update.yml` | Push to a branch other than the base branch (`--base-branch`) leaving indexed docs stale or missing | AI-powered audit + update on feature branches |
| `doc-review-pr.yml` | PR open/sync touching indexed docs; `@claude` PR comment | AI-powered PR doc review (a fixed-prompt job), and tag mode for `@claude` |
| `doc-release.yml` | Push to `release/**` | AI-powered release-notes drafting, opened as a PR |
| `doc-spec-verify.yml` | PR open/sync touching indexed specs; its `claims` job on every same-repository PR (never forks or Dependabot) | Verifies spec compliance against changed code; the `claims` job (no AI) checks the spec claims and posts the amendment batch |
| `doc-pr-full-cycle.yml` | PR open touching indexed docs | Superset of review-pr — runs review + update + diagram + sync |
| `doc-pr-release.yml` | PR open/sync/reopen | Drafts/maintains `RELEASE-NOTES.next/PR-<N>.md` fragments and the managed `<!-- doc-superpowers:start/end -->` section of the PR body |
| `doc-ledger-publish.yml` | Every 30 minutes (`*/30 * * * *`); `workflow_dispatch` | Publishes the work-ledger views (`ledger publish`, `references/ledger.md`); no AI; one run at a time (`concurrency: doc-ledger-publish`, never cancelled); on a ledger host, ships the ledger helper set; skipped by `--workflows=all` without `docs/ledger/config.json` |

The `doc-pr-release.yml` workflow uses shell helpers installed alongside
it at `.github/scripts/doc-pr-release/`:
- `extract-context.sh` — emits JSON context: PR body, the fragment and its computed hash state, and the PR's own commits (never base-branch or bot commits) since the checkout the last sync recorded
- `update-pr-body.sh` — idempotent marker-based PR body merge (markers inside code fences are ignored; an END before the START is refused, and so is a body ending inside an unclosed fence when it has no default section yet — appending would land inside the fence; a new named section goes at the top, above it, so it is never refused for that). `DOC_SUPERPOWERS_SECTION=<name>` (`[a-z0-9-]+`, else exit 2) edits a named section instead, `<!-- doc-superpowers:<name>:start -->` / `<!-- doc-superpowers:<name>:end -->`, inserted at the top of the body when new; content holding any section's marker is refused. `doc-spec-verify.yml`'s `claims` job writes the `spec-claims` section with it, only while this helper is installed (its step tests `hashFiles(…)`, so installing `doc-spec-verify` alone does not ship these helpers)
- `fragment-lib.sh` — the fragment line rules (markers, hash line, sha256) the helpers source
- `commit-and-push.sh` — seals the fragment (writes its line-2 hash), commits only that file, and pushes it only while the branch is still at the checkout (`--force-with-lease` on the checkout: someone else's push → superseded, exit 0; a force-push or reset → exit 1, never undone); never overwrites a hand-edited fragment, and refuses (exit 1) one the release would skip — text before the first `###`, a `#`/`##` heading, an unclosed code fence — checked with the vendored `doc-tools.sh fragments list`, so the author learns it at PR time

The templates' `run:` steps are scripts in
