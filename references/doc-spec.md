## Freshness Marker

Add this HTML comment as the first line of every generated doc file:

```
<!-- Generated by doc-superpowers -->
```

The marker identifies a generated doc, for example to find flat-structure docs to migrate. It carries no date or commit. Freshness is recorded in one place only, `docs/.doc-index.json`: each entry's `code_oids` and `last_verified` (see [Doc-Index Schema Reference](#doc-index-schema-reference)). A date and commit in the doc would be a second freshness claim that nothing reads, and it would go stale. A marker from an older release, `<!-- Generated by doc-superpowers | YYYY-MM-DD | commit: SHORT_HASH -->`, is still recognized and may be left as it is.

<!-- Why this spec is needed -->

<!-- Key implementation considerations -->

<!-- How to verify the implementation matches this spec -->

`Draft`, `In Review`, `Approved`, and `Implemented` form the ladder that `spec-inject` transitions automatically (`spec-verify` is read-only — it reports on `Status` and never writes it). `Active` (continuously-evolving reference specs), `Deprecated`, `Superseded`, **and any status not on that ladder** sit outside it and are never transitioned by automation — the exempt class is open-world, so a status added later cannot fall back to an unguarded write. ### Workflow Depth Guidance

When generating agentic workflow docs, use this table to decide how many diagrams a skill needs:

| Depth | When to use | Diagram type |
|---|---|---|
| **Overview** | Always — shows how commands/skills relate | Single flowchart with all commands as entry points |
| **Workflow** | Each skill with 2+ phases | Subgraph flowchart + sequence diagram |
| **Internals** | Complex pipelines only (4+ sub-agents, batching, recovery) | State diagram + detailed sequence with script-level lifelines |

Rule of thumb: every skill gets overview + workflow depth. Only add internals depth if the pipeline has state tracking, auto-batching, or recovery flows.

## CLAUDE.md Updates

CLAUDE.md is loaded at the start of every Claude session. Stale entries mean every future session starts with incorrect context about the project. This makes CLAUDE.md sync a critical step — not just for `init`, but for every write action that changes project structure.

**When to apply these rules**: After ANY doc-superpowers write action that changes directory structure, adds/removes files, or modifies commands. This includes `init`, `update`, `spec-generate`, `sync`, and `release`. The `audit` and `review-pr` actions detect CLAUDE.md staleness and report it; the write actions fix it.

**If CLAUDE.md exists**: Read it first. Only update sections that are factually stale:
- **Directory Structure**: Sync the tree with actual filesystem (new dirs, removed dirs, renamed paths)
- **Key Files**: Update the table if files were added, removed, or changed purpose
- **Commands**: Add/remove any slash commands or scripts that changed
- **File references**: Update paths, line counts, or descriptions that no longer match
- **Category/enum lists**: Sync with code if the canonical list lives in CLAUDE.md

**Preserve everything else** — tone, workflow descriptions, extraction rules, conventions, and any manually-written guidance. Do NOT rewrite sections that are still accurate. Do NOT reformat or restructure. Treat CLAUDE.md as the project owner's voice.

**If CLAUDE.md does not exist**: Create one with these sections:

```markdown
# [Project Name]

[1-2 sentence description]

## Quick Start

\`\`\`bash
# Essential setup/run commands
\`\`\`

## Directory Structure

\`\`\`
project/
├── dir/    # description
└── file    # description
\`\`\`

## Commands

- `/command` - description

## Key Files

| File | Purpose |
|------|---------|
| | |

## Conventions

<!-- Project-specific patterns, naming rules, important constraints -->
```

Keep it concise — CLAUDE.md should be a quick-reference entry point, not a comprehensive doc (that's what `docs/` is for).

## README.md Updates

README.md is the project's public documentation — if it lists outdated features or missing actions, users and contributors don't know what the tool can do. Like CLAUDE.md, README.md sync is a cross-cutting concern for every write action.

**When to apply these rules**: After ANY doc-superpowers write action that changes capabilities, actions, features, or project structure. This includes `init`, `update`, `sync`, `release`, and `spec-generate`. The `audit` and `review-pr` actions detect README.md staleness and report it; the write actions fix it.

**If README.md exists**: Read it first. Only update sections that are factually stale:
- **Feature list**: Sync with actual SKILL.md actions and capabilities
- **Action list**: Sync with action definitions (init, audit, review-pr, update, diagram, sync, hooks, release, spec-*)
- **Usage examples**: Verify examples still work and reference current action names/flags
- **Project description**: Ensure it covers current major capabilities

**Preserve everything else** — tone, structure, installation instructions, contributing guidelines, and any manually-written content. Do NOT rewrite sections that are still accurate. Do NOT reformat or restructure. Treat README.md as the project owner's voice.

**If README.md does not exist**: Do not create one — README.md is the project owner's responsibility. Flag as P2 Incomplete in audit if the project has docs but no README.md.

## Doc-Index Schema Reference

Schema for `docs/.doc-index.json`. Generated by `scripts/doc-tools.sh build-index`.

**Key form.** Entries are keyed by paths **relative to the repo root** (`docs/architecture.md`, never `/Users/me/proj/docs/architecture.md`). Every consumer — `update-index`, `check-freshness`, `status`, `remove-entry`, `move-entry`, `deprecate-entry`, the CI coverage gate, and the merge driver — looks entries up by that exact string, so an absolute or `./`-prefixed key is one nothing can find. The subcommands normalize an absolute in-tree path to its relative form and reject anything outside the working tree with a non-zero exit; run `doc-tools.sh` from the repo root so relative paths resolve as intended. The same rule applies to path-valued fields (`replaces`, `superseded_by`) — which is why `move-entry` repoints any other entry's `replaces`/`superseded_by` that named the old path, rather than leaving it dangling at a key nothing can resolve.

**Writing entries.** `build-index` and `add-entry` read one mapping line per doc on stdin: `doc_path:code_refs_csv:doc_type` (e.g. `docs/architecture.md:SKILL.md,scripts/:architecture`). `:` separates the fields, so a doc path or ref must not contain one. A line is rejected when it has no `:` (a bare path, which would otherwise be split into refs and type) or more than two. It is also rejected when its first field is not a file but its first two or three fields joined by `:` name one on disk, since that file would otherwise be indexed under the wrong key. A `:` path whose file does not exist yet cannot be detected. `doc_type` may be empty. Refs are split on `,`, trimmed, and empty ones dropped. The same list is stored as `code_refs` and handed to git. A trailing CR is stripped. A ref is a literal path: a file, a directory, or `.` for the whole repository. It is never a glob. git sees refs with `--literal-pathspecs`, and a ref containing `*`, `?` or `[` draws a warning, because it names only a path of exactly that name. (An entry written before index schema 3 keeps git's pathspec reading, globs included, until it is re-verified.) A ref that does not exist and matches no file tracked by git also draws a warning. It is recorded as `missing`, and HEAD agrees, so the doc cannot go stale until that path is committed. Untracked (not ignored) files under a ref are part of what is verified: writers stage them (`git add -A` on a private index) and name them in a warning, and the doc reads stale until they are committed or ignored. A key listed twice keeps its first line. `add-entry` applies the valid lines and exits 1 if any was rejected. `build-index` writes nothing if any line is invalid or none is given, and refuses to replace an index that has entries unless given `--force` (which discards their metadata, deprecations included). Doc paths given anywhere are normalized to the key form: `//` becomes `/`, a path starting with `-` is refused, and a repeated path counts once.

**Command line.** Options may appear anywhere, and `--opt VALUE` equals `--opt=VALUE`; `--` ends the options. `<subcommand> --help` prints its usage and exits 0 (it needs neither jq nor a repository). Exit status: `0` success; `1` the operation failed or was refused; `2` usage error: an unknown subcommand or option, an option without its value, the wrong number of arguments (including any argument to a subcommand that takes none), or a repository subcommand run outside a git work tree. A malformed argument value, such as `bump-version abc`, exits `1`. An unknown option is never ignored, and nothing is written. `update-index` reports and skips a path that is not indexed, applies the rest, then exits 1. `check-freshness --code-refs <path>...` (every argument up to the next `--option`) or `--code-refs-from <file|->` (one path per line; `-` is stdin, with no argv limit) keeps the docs whose `code_refs` share a path segment with a listed path. `src/m1` matches refs `src/m1`, `src/m1/a.js` and `src/`, but never `src/m10`. `.` is the repository root, and an empty list keeps nothing. Produce the list with `git -c core.quotePath=false diff --name-only --no-renames`. `check-freshness` and `status` share one evaluation, so they cannot disagree about a doc. Both compare against HEAD, or against the tree given with `--tree <tree-ish>`. A pre-commit check passes `--tree "$(git write-tree)"`, the staged tree, so it sees the change being committed. A `--tree` value may not start with `-` (exit 2), and one that names no tree exits 1. A stored `code_commit` that is not a full hex object id is treated as absent and never passed to git.

**Renames.** When a doc moves, use `move-entry <old> <new>` — it re-keys the entry and preserves `code_refs`, `code_oids`, `code_commit`, `last_verified` and every other field, recomputing only `content_hash`. Do **not** use `remove-entry` + `add-entry`: that drops `code_refs`, and an entry with no refs has nothing for `check-freshness` to compare against, so it reports `current` unconditionally and forever.

**Freshness.** A doc is stale when the content of one of its code refs differs from the content it was verified against. The index records that content, not the commit that last touched it. For each ref, `code_oids` holds the git object id of its content: a blob for a file, a tree for a directory, or `missing`. Writers capture it from the working tree (through a private git index, so git's own staging is never touched), because that is what the verifier read. `check-freshness` looks every ref of the index up in HEAD, or in `--tree`, in one `git cat-file --batch-check`. So a squash merge, a GitHub rebase-merge, a cherry-pick, a revert to the verified bytes, a shallow clone, and a doc verified in the same commit as its code all read `current` when the bytes match. For a stale doc, `code_refs_changed` lists exactly the refs whose object id differs. `commits_behind` is `git rev-list --count <code_commit>..HEAD -- <refs>`, and it is `null` when `code_commit` is not an ancestor of HEAD here: the repository does not have it (a squash-merged branch was deleted, or the clone is shallow), or it is on another line of history (only the verify commit was cherry-picked). It is never a masked `0`. A ref naming a submodule records the submodule's commit (its gitlink entry, resolved with `git ls-tree` because the commit is not in the superproject's object store), so a submodule bump reads stale. The doc-index file itself, with its lock and tmp files, is excluded from the content of any ref that covers it (`docs/`, `.`), because otherwise every index write would make that doc stale. An entry without `code_oids` (written before schema 3) is judged the old way until a writer re-verifies it: stale when the newest commit touching its refs is not `code_commit`.

| Field | Type | Purpose |
|-------|------|---------|
| `schema_version` | integer | Index schema: `3` (per-ref `code_oids`). A `2` index is read as it is. So is an older one that carries `version: 1` instead. The first write stamps `3` and drops `version`; a run that changes nothing leaves the index untouched |
| `generated_by` | string | Always `"doc-superpowers"` |
| `generated_at` | ISO 8601 | When the index content last changed (a writer run that changes nothing leaves it untouched) |
| `build_commit` | string\|null | Repo HEAD at last `build-index` (null on an unborn HEAD) |
| `docs.<path>.content_hash` | string\|null | `sha256:<hex>` of the doc's bytes. It is null when `add-entry` indexed a doc that was not on disk yet; that doc reads `doc_modified` until `update-index` |
| `docs.<path>.code_refs` | string[] | The literal paths this doc covers: files, directories, or `.` for the repository root |
| `docs.<path>.code_oids` | object | One key per ref (as stored in `code_refs`), holding the git object id of its content when the doc was last verified: a blob id, a tree id, or `"missing"`. Freshness is judged against this. It is written by `build-index`, `add-entry` and `update-index`, carried over by `move-entry`, and absent on entries written before schema 3 |
| `docs.<path>.code_commit` | string\|null | The newest commit touching the refs when the doc was verified. It is the `commits_behind` baseline and is shown to older readers; it does not decide freshness. It is null when no commit touches the refs, on an unborn HEAD, or when the entry was written in a shallow clone (whose truncated history would name the graft, so writers refuse it) |
| `docs.<path>.doc_type` | string | Template type |
| `docs.<path>.status` | enum | As stored: `current` \| `deprecated`. `stale` and `missing` are computed by `check-freshness`, which never writes |
| `docs.<path>.replaces` | string\|null | Path to superseded doc |
| `docs.<path>.superseded_by` | string\|null | Path to superseding doc |
| `docs.<path>.last_verified` | ISO 8601 | When a writer last recorded the entry: `build-index`, `add-entry`, `update-index`, and also `deprecate-entry` |
| `docs.<path>.implementation` | string[] | Written by `update-index` only: the bullets of an ADR's `Implementation:` or a SPEC's `Realized-by:` block, with the leading `  - ` stripped (see `implementation-status`) |

### Status Transitions

- `current` → `stale`: reported by `check-freshness` when a code ref's content no longer matches `code_oids` (read-only, doesn't write index)
- `stale` → `current`: set by `update-index` after doc regeneration
- `current` → `deprecated`: human-set only, never overridden by tooling
- `deprecated` is terminal for automated tools
